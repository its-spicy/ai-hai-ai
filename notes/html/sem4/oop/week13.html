1. Why These Four Tools Matter

The problem. Imagine you are building a student-management system. Sooner or later you must (a) duplicate a student's record without disturbing the original, (b) read data from a keyboard or a file and write results out, (c) save an object to disk so that it survives after the program closes, and (d) organise hundreds of classes so that they do not become a tangled mess.

Java has one mechanism for each of these needs:

Concept Main purpose Example application
Cloning Creating copies of objects Duplicating student records
I/O (Input/Output) Reading and writing data Reading files and console input
Serialization Converting object state into bytes Saving an employee object to a file
Packages Organising related classes Grouping related classes (e.g., com.university)

These concepts are essential for banking systems, student management software, distributed applications, file management systems, and network-based services. In this chapter we study them one by one and finish with a single program that combines all four.

2. Object Cloning

2.1 The problem and the idea

The problem. A banking system wants to simulate a transaction on an account to see what the balance would become — without touching the real account. If the simulation works directly on the real object, the real balance changes.

The intuitive idea. Make a copy of the object and run the simulation on the copy.

The analogy. A photocopy of a form is a new sheet of paper with the same writing. Scribbling on the photocopy does not change the original. Where the analogy stops: if the form says "see the attached sheet in the office drawer", both the original and the photocopy point to the same attached sheet. Change that sheet and both forms "see" the change. This is exactly the shallow-copy problem in Section 2.5.

Reference assignment is not cloning. These two lines look similar but do very different things:

Student s2 = s1;          // NOT a copy: one object, two names (references)
Student s3 = s1.clone();  // a NEW object with the same field values

2.2 What is object cloning?

Object cloning is the process of creating a new object whose field values are copied from an existing object. In Java it is performed with the clone() method of the Object class, although copy constructors and factory methods are often preferred in modern application design.

General syntax:

ClassName obj2 = (ClassName) obj1.clone();

The cloned object (obj2) is a separate object with its own identity, so obj1 == obj2 is false. However, its internal references may still point to the very same objects as the original. A student-management application can use this to duplicate a student's information without simply creating another reference to the original object. The diagram on the right shows the flow: the original goes through clone() and a new object appears with the same data but a new identity.

Why do we need cloning? Cloning is useful when we want to:

  • Create a copy of an object without modifying the original.
  • Preserve an object's state before performing operations.
  • Duplicate configuration objects or application data.
  • Implement simulations and independent object processing.
  • Avoid manually copying numerous fields.

2.3 The Cloneable interface

Java provides the Cloneable marker interface in the java.lang package.

  • A marker interface declares no methods. It only signals that the class permits field-by-field cloning using Object.clone().
  • Object.clone() is protected, so a class generally exposes its own public clone() method.
  • Calling Object.clone() on an instance of a class that does not implement Cloneable normally results in a CloneNotSupportedException.
  • The default cloning operation copies primitive values and references, but does not recursively clone the referenced objects.

The standard pattern for a clonable class is:

@Override
public ClassName clone() throws CloneNotSupportedException {
    return (ClassName) super.clone();
}
Part Meaning
@Override Tells the compiler we are replacing Object's clone(); it reports an error if the signature does not match.
public Object.clone() is protected; making ours public lets code outside the class call it.
ClassName (return type) We may narrow the return type from Object to our own class (a covariant return type), so callers need no cast.
throws CloneNotSupportedException A checked exception: the caller must catch it or declare it. Object.clone() throws it when Cloneable is missing.
super.clone() Calls the Object version, which does the field-by-field copy.
(ClassName) cast super.clone() returns Object; we cast it back to our class.

Common mistake (labelled invalid): forgetting implements Cloneable.

// INVALID DESIGN: compiles, but fails when clone() is called
class Student {                       // missing: implements Cloneable
    public Student clone() throws CloneNotSupportedException {
        return (Student) super.clone();
    }
}

This compiles, but at runtime super.clone() throws CloneNotSupportedException. Forgetting the throws clause (or a try/catch) instead gives a compile-time error, because the exception is checked.

2.4 Cloning a Student object

Goal: make a copy of a Student and prove that the copy is a different object with the same data.

The class Student implements Cloneable, which grants permission to clone. It has two fields, rollNo (an int) and name (a String). In the constructor, this.rollNo = rollNo; means "store the parameter rollNo into this object's field rollNo"; this is what separates the field from the parameter that has the same name. The clone() method follows the standard pattern from Section 2.3, and display() simply prints the state. Because display() returns nothing, its return type is void; it prints the values instead of returning them. 

class Student implements Cloneable {
    int rollNo;
    String name;

    Student(int rollNo, String name) {
        this.rollNo = rollNo;
        this.name = name;
    }

    @Override
    public Student clone()
            throws CloneNotSupportedException {
        return (Student) super.clone();
    }

    void display() {
        System.out.println(rollNo + " " + name);
    }
}

The driver class (main must declare throws CloneNotSupportedException because clone() does):

public class CloningExample {
    public static void main(String[] args)
            throws CloneNotSupportedException {
        Student s1 = new Student(101, "Rahul");
        Student s2 = s1.clone();

        System.out.println("Original Object:");
        s1.display();
        System.out.println("Cloned Object:");
        s2.display();
        System.out.println(s1 == s2);
    }
}

Output:

Original Object:
101 Rahul
Cloned Object:
101 Rahul
false

Execution trace:

Step Operation Result
1 new Student(101, "Rahul") Constructor runs; s1 refers to the first object
2 s1.clone() Object.clone() creates a new Student with rollNo = 101 and the same name reference
3 Assign to s2 s2 refers to the second object
4 display() on both Both print 101 Rahul (same data)
5 s1 == s2 == compares references, not contents; they are different objects, so false

Note for Review: == on objects asks, "Are these the same object?" It does not ask, "Do they hold equal data?" After cloning, the data is equal but the answer to == is false.

2.5 Types of cloning: shallow and deep

The two major types of object copying discussed in Java are shallow copying and deep copying.

Shallow copy Deep copy
New outer object? Yes Yes
Nested objects Both objects share the same nested object Nested mutable objects are also copied
Effect of changing the nested object through the clone The original changes too The original is unaffected

Shallow cloning

Shallow cloning creates a new outer object but copies the references to nested objects.

Here an Employee has an Address. The name field is a String, which is immutable, so sharing it is harmless. The address field, however, refers to a mutable Address object. The clone() method here is just super.clone(), which copies the reference stored in address rather than building a new Address. That single detail is what makes this a shallow clone. 

class Address {
    String city;
    Address(String city) {
        this.city = city;
    }
}

class Employee implements Cloneable {
    String name;
    Address address;

    Employee(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    public Employee clone()
            throws CloneNotSupportedException {
        return (Employee) super.clone();
    }
}
public class ShallowCloneDemo {
    public static void main(String[] args)
            throws CloneNotSupportedException {
        Employee e1 = new Employee("Amit", new Address("Delhi"));
        Employee e2 = e1.clone();
        e2.address.city = "Mumbai";
        System.out.println(e1.address.city);
        System.out.println(e2.address.city);
    }
}

Output:

Mumbai
Mumbai

Why did changing e2 change e1? Trace the memory:

Step Operation State
1 Create e1 e1 → Employee(Amit, address → A1), where A1 is Address(city = Delhi)
2 e2 = e1.clone() e2 → a new Employee(Amit, address → A1); only the reference was copied
3 e2.address.city = "Mumbai" Follows the reference to A1 and changes its city
4 Print both e1.address and e2.address both lead to A1, so both print Mumbai

The diagram shows the shallow-copy situation. e1 and e2 are different Employee objects, but both of their address references lead to one shared Address object. Any change made through either employee is visible through the other. This is the same as two photocopied forms that both point to one attached sheet.

Deep cloning

Deep cloning creates a separate copy of the nested objects too, so changes in the clone do not affect the original. The fix is to build a new Address inside clone().

Only the clone() method of Employee changes; Address, the constructor, and the demo class stay the same. First, super.clone() makes the shallow copy. Then the second line replaces the shared reference in the copy with a brand-new Address built from the old city. After this, the original and the clone each own a separate Address object, which is the definition of a deep copy for this class. 

@Override
public Employee clone()
        throws CloneNotSupportedException {
    Employee copy = (Employee) super.clone();
    copy.address = new Address(this.address.city);
    return copy;
}

Running the same main as before now gives:

Delhi
Mumbai
Step Operation State
1 Create e1 e1 → Employee(Amit, address → A1: Delhi)
2 e1.clone() Shallow copy first; then copy.address is replaced with a new A2: Delhi
3 e2.address.city = "Mumbai" Changes A2 only
4 Print both e1 prints Delhi, e2 prints Mumbai

Note for Review: Shallow copy copies only the outer object, and both objects share the same nested object. Deep copy copies the outer object and also creates new copies of the nested objects. Strings and primitives need no special treatment; mutable nested objects do.

2.6 The copy constructor

A copy constructor is a constructor that creates a new object by copying the state (data member values) of an existing object of the same class. It takes a parameter of its own class type.

The class Student now has two constructors. Student(int rollNo, String name) initialises a brand-new object from raw values. Student(Student other) is the copy constructor: it reads the fields of other and stores them in this new object. The call new Student(s1) therefore builds s2 as a separate object with the same values as s1. No Cloneable, no super.clone(), no cast, and no checked exception is needed. 

class Student {
    int rollNo;
    String name;

    // Parameterized constructor
    Student(int rollNo, String name) {
        this.rollNo = rollNo;
        this.name = name;
    }

    // Copy constructor
    Student(Student other) {
        this.rollNo = other.rollNo;
        this.name = other.name;
    }
}
public class CopyConstructorDemo {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul");
        Student s2 = new Student(s1);

        System.out.println(s2.rollNo);
        System.out.println(s2.name);
    }
}

Output:

101
Rahul

Both s1 and s2 have the same values, but they are separate objects. Java chooses between the two constructors by the argument types (int, String versus Student).

Supplementary comparison. A copy constructor makes copying explicit and visible: you decide field by field whether to share or copy. If a class had a mutable nested object, the copy constructor would have to create a copy of it as well (as in the deep-clone example). This explicitness is why copy constructors and factory methods are often preferred over clone() in modern design.

3. Input and Output in Java

3.1 The problem and the idea

The problem. A program that cannot receive data or show results is useless. Also, data stored only in variables vanishes when the program ends, so we need files.

The analogy. Think of a water pipe. Water (data) flows through it in order, in one direction, until the source runs dry. Java calls such a pipe a stream. Where the analogy stops: unlike water, data in a stream is read as separate bytes or characters, and the end of the stream is signalled by a special value (-1).

Input/Output (I/O) refers to the mechanism through which a program receives information from external sources and sends information to external destinations.

  • Input: reading data from a keyboard, file, network connection, or another source.

  • Output: writing data to the console, file, network connection, or another destination.

    Data flows from an input source, through the Java program, to an output destination. Keyboard, file, and network connections can all be sources, and console, file, and network connections can all be destinations. Java provides the classes for this through several packages. The packages are summarised in the table below: java.io is the traditional, stream-based one that most of this chapter uses.

Package Role
java.io Traditional stream-based I/O
java.nio Buffers, channels, and related APIs
java.nio.file File-system operations
java.util Utilities such as Scanner

3.2 Categories of streams

Java I/O streams can be categorised as byte streams, character streams, buffered streams, data streams, and object streams.

Category Works with Typical classes
Byte streams Raw 8-bit bytes InputStream, OutputStream
Character streams Text characters (supplementary) Reader, Writer
Buffered streams Adds a memory buffer for efficiency BufferedInputStream, BufferedOutputStream
Data streams Java primitive values DataInputStream, DataOutputStream
Object streams Whole objects (used for serialization) ObjectInputStream, ObjectOutputStream

3.3 Byte streams

Byte streams operate on bytes (8-bit data) and are useful for binary files such as images, audio files, and executable data.

  • The two abstract base classes are InputStream (for reading bytes) and OutputStream (for writing bytes).
  • Common use cases: images (.jpg, .png), audio (.mp3, .wav), video (.mp4, .avi), and executable files (.exe, .class).
  • They work at the byte level, provide low-level, efficient I/O, and suit binary data (images, audio, executables, serialized objects).
Input classes (extend InputStream) Output classes (extend OutputStream)
FileInputStream FileOutputStream
BufferedInputStream BufferedOutputStream
DataInputStream DataOutputStream
ObjectInputStream ObjectOutputStream

Note for Review: InputStream and OutputStream are abstract, so you cannot create objects of them directly. You create objects of their concrete subclasses such as FileInputStream. (Some of these, such as the buffered and data streams, extend the base class indirectly through an intermediate class.)

3.4 Writing data with FileOutputStream

Goal: write the text Welcome to Java Programming into a file called data.txt.

How it works: String → convert to bytes (UTF-8) → FileOutputStream writes bytes → data.txt.

A computer file stores bytes, not Java String objects, so the message is first converted to a byte[] using getBytes(StandardCharsets.UTF_8); UTF-8 is the character encoding that decides which numbers stand for which characters (for example W = 87, e = 101, l = 108). Then fos.write(data) sends the array to the file. The try ( ... ) form is called try-with-resources: the stream declared in the parentheses is closed automatically when the block ends, even if an error occurs. Because file operations can fail, FileOutputStream can throw the checked IOException, which is caught in the catch block. 

import java.io.FileOutputStream;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

public class WriteFileDemo {
    public static void main(String[] args) {
        String message = "Welcome to Java Programming";

        try (FileOutputStream fos =
                 new FileOutputStream("data.txt")) {
            byte[] data = message.getBytes(
                    StandardCharsets.UTF_8);
            fos.write(data);
            System.out.println("File written successfully");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Key steps:

Step Operation Result
1 Create a FileOutputStream for "data.txt" File opened for writing
2 getBytes(StandardCharsets.UTF_8) String becomes a byte array
3 fos.write(data) Bytes are written to the file
4 End of the try block Stream closed automatically

Console output: File written successfully
Contents of data.txt: Welcome to Java Programming

Supplementary: by default, new FileOutputStream("data.txt") creates the file if it does not exist and overwrites it if it does.

3.5 Reading data with FileInputStream

Goal: read a file byte by byte and display it. Suppose data.txt contains:

Hello Java!
FileInputStream Demo.

fis.read() reads one byte and returns it as an int in the range 0–255, or -1 when the end of the file is reached. It returns int rather than byte so that -1 can be told apart from every valid byte value. The loop condition (data = fis.read()) != -1 does two jobs: it assigns the byte to data, and then compares the result with -1. The parentheses around the assignment are required. Casting with (char) data turns the number back into a printable character. 

import java.io.FileInputStream;
import java.io.IOException;

public class ReadFileDemo {
    public static void main(String[] args) {
        try (FileInputStream fis =
                 new FileInputStream("data.txt")) {
            int data;
            while ((data = fis.read()) != -1) {
                System.out.print((char) data);
            }
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Output (console):

Hello Java!
FileInputStream Demo.

Note for Review (accuracy): converting each byte straight to a char works for plain English (ASCII) text, where one character equals one byte. Characters that need several bytes in UTF-8 would be displayed wrongly this way. For general text, the character streams (Reader/Writer classes) are the better tool.

3.6 Reading from the keyboard with Scanner

So far, values in our programs were fixed in the code. To take input from the user, we use the Scanner class from java.util.

The problem. A grading program that has int marks = 85; written into the code gives the same answer every time. We want the user to type the marks.

General pattern:

import java.util.Scanner;                // 1. import the class

Scanner sc = new Scanner(System.in);     // 2. create a Scanner object on the keyboard
String text = sc.nextLine();             // 3. read a whole line (String)
int number  = sc.nextInt();              // 3. read an integer
sc.close();                              // 4. close it when finished

System.in is the keyboard input stream, and new Scanner(System.in) wraps it in an object with convenient reading methods. sc.nextLine() reads a line of text for a String, and sc.nextInt() reads an integer for an int. The import is mandatory because Scanner lives in the java.util package (you may write import java.util.*; instead). The public class name must match the file name, so this class must be saved as InputDemo.java. Finally, sc.close() releases the Scanner. 

import java.util.Scanner;

public class InputDemo {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);

        System.out.print("Enter your name: ");
        String name = sc.nextLine();

        System.out.print("Enter your age: ");
        int age = sc.nextInt();

        System.out.println("Name = " + name);
        System.out.println("Age = " + age);

        sc.close();
    }
}

Sample run (the user types Devasis and 35):

Enter your name: Devasis
Enter your age: 35
Name = Devasis
Age = 35

Common mistakes:

Mistake What Java does
Using sc (or sc.close()) before the line Scanner sc = new Scanner(System.in); Compile-time error: sc is not defined yet. Always declare the Scanner first.
Typing text where nextInt() expects a number Runtime exception (InputMismatchException): the input is not an integer.
Forgetting the import Compile-time error: Java cannot find Scanner.
Public class name differs from the file name Compile-time error: a public class must be in a file with the same name.

Note for Review: reading a name with nextLine() and then a number with nextInt() (in that order, as above) is safe. Reversing the order can leave the Enter key press unread, so a following nextLine() appears to be skipped.

4. Serialization

4.1 The problem and the idea

The problem. A Student object lives only in memory. When the program ends, it is gone. How can we save it and restore it later, or send it to another Java application?

The analogy. Flat-pack furniture. A wardrobe is too bulky to post, so the factory takes it apart into a box of parts (a stream of bytes). The box can be stored or shipped, and the wardrobe is reassembled later at the destination. Where the analogy stops: reassembly needs the "instruction manual", which in Java is the class definition. The class must be available when the object is rebuilt.

Serialization is the process of converting an object's state into a byte stream so that it can be stored or transmitted. The reverse process is deserialization. Serialization allows an object's state to be preserved beyond the lifetime of a running program.

The diagram shows the workflow. A Student object is serialized into a byte stream (here stored in student.ser), and deserialization rebuilds the object from those bytes. The byte stream can then be placed in files, databases, or sent across a network. Serialization is useful for saving object states to disk, transferring object data between Java applications, preserving application state, supporting legacy Java remoting and object-storage mechanisms, and demonstrating persistence of Java objects.

For example, a student management application can save a Student object to a file, terminate, and later restore an equivalent object state.

Note for Review: for modern web APIs, JSON or other explicitly defined data formats are often preferable to native Java object serialization, particularly when interacting with systems written in different languages.

4.2 The Serializable interface

Java provides the Serializable marker interface (in java.io):

import java.io.Serializable;

class Student implements Serializable {
    int rollNo;
    String name;
}

This interface does not define methods. It marks objects of the class as eligible for Java's built-in object serialization mechanism. The two main classes are:

  • ObjectOutputStream: writes objects.
  • ObjectInputStream: reads objects.

implements versus extends, since this chapter uses both: a class may extend only one class, but may implement any number of interfaces, separated by commas (for example, implements Serializable, Cloneable).

4.3 Serializing a Student object

The class Student has three fields: rollNo, name, and marks. The line private static final long serialVersionUID = 1L; is a version identifier for the class. Java compares it when an object is deserialized, to check that the saved data matches the class definition. It is recommended rather than mandatory. It is static because it belongs to the class, final because it never changes, and long because that is the type Java requires. If the stored ID and the class ID differ, deserialization fails with an InvalidClassException. 

import java.io.*;

class Student implements Serializable {
    private static final long serialVersionUID = 1L;

    int rollNo;
    String name;
    double marks;

    Student(int rollNo, String name, double marks) {
        this.rollNo = rollNo;
        this.name = name;
        this.marks = marks;
    }
}
public class SerializationDemo {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul", 92.5);

        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream("student.ser"))) {
            oos.writeObject(s1);
            System.out.println("Object serialized successfully");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Output: Object serialized successfully (and a binary file student.ser appears).

Two layers of streams. Look at the constructor chain new ObjectOutputStream(new FileOutputStream("student.ser")):

  • FileOutputStream handles the file's byte output (it knows how to reach the file).
  • ObjectOutputStream handles Java object serialization (it converts the object into bytes).

Streams provide the data transport (file, network, etc.), while serialization handles the object conversion.

The diagram shows how the writing side works. writeObject(s1) hands the object to the ObjectOutputStream, which converts it to a serialized byte representation and passes those bytes to the underlying FileOutputStream, which stores them in the file. Reading is the mirror image: FileInputStream reads the bytes from storage, and ObjectInputStream interprets the serialization format and reconstructs the object.

Step Operation Result
1 new Student(101, "Rahul", 92.5) Object created in memory
2 Open FileOutputStream("student.ser"), wrap in ObjectOutputStream Two-layer stream ready
3 oos.writeObject(s1) Object state converted to bytes and written
4 End of try Streams closed automatically
5 println Object serialized successfully

4.4 Deserializing the object

Deserialization is the process of reading a serialized object from a file (a sequence of bytes) and reconstructing it into an object in memory.

public class DeserializationDemo {
    public static void main(String[] args) {
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream("student.ser"))) {
            Student s = (Student) ois.readObject();
            System.out.println("Roll No: " + s.rollNo);
            System.out.println("Name: " + s.name);
            System.out.println("Marks: " + s.marks);
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

(The lecture repeats the same Student class, with the same fields and serialVersionUID, above this program. In a real project there is one shared Student.java.)

Output:

Roll No: 101
Name: Rahul
Marks: 92.5

Syntax breakdown:

Piece Meaning
new ObjectInputStream(new FileInputStream("student.ser")) Open the file as bytes, then wrap it to interpret those bytes as objects
ois.readObject() Reads the next object. Its return type is Object
(Student) Cast needed to treat the returned Object as a Student
IOException | ClassNotFoundException Multi-catch: one handler for two exception types. ClassNotFoundException occurs if the class of the saved object cannot be found

Key steps: (1) open student.ser with FileInputStream; (2) wrap it with ObjectInputStream; (3) read with readObject() and cast to Student; (4) access and print rollNo, name, marks.

Supplementary: the serialization mechanism restores the field values from the bytes; it does not run the constructor of the serializable class again.

4.5 Complete round trip: saving and restoring in one program

Practical example: student record persistence. Using the Student class from Section 4.3, the program saves a student, then reads it back.

Student student = new Student(101, "Rahul", 92.5);

// Serialize: save the object to disk
try (ObjectOutputStream oos = new ObjectOutputStream(
        new FileOutputStream("student.ser"))) {
    oos.writeObject(student);
    System.out.println("Student saved to disk.");
}

// Deserialize: read the object back from disk
try (ObjectInputStream ois = new ObjectInputStream(
        new FileInputStream("student.ser"))) {
    Student recovered = (Student) ois.readObject();
    System.out.println("Recovered Student:");
    System.out.println(recovered.rollNo + " " + recovered.name
            + " " + recovered.marks);
}

(This fragment belongs inside a main that handles or declares the exceptions, as in the previous sections.)

Output:

Student saved to disk.
Recovered Student:
101 Rahul 92.5

This enables persistent storage of student records for later use, for example in student information systems, university management portals, and anything that persists records across sessions.

4.6 A complete Student Management example

Goal: create a Student, save it into students.ser, restore it into a new object, and display it using a display() method.

import java.io.*;

class Student implements Serializable {
    private static final long serialVersionUID = 1L;
    int rollNo;
    String name;
    String department;

    Student(int rollNo, String name, String department) {
        this.rollNo = rollNo;
        this.name = name;
        this.department = department;
    }

    void display() {
        System.out.println("Roll No: " + rollNo);
        System.out.println("Name: " + name);
        System.out.println("Department: " + department);
    }
}
public class StudentManagement {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul", "CSE");

        // Serialize: save the student object
        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream("students.ser"))) {
            oos.writeObject(s1);
            System.out.println("Student saved.");
        } catch (IOException e) {
            e.printStackTrace();
            return;
        }

        // Deserialize: read the student object
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream("students.ser"))) {
            Student s2 = (Student) ois.readObject();
            System.out.println("Student restored:");
            s2.display();
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

Output:

Student saved.
Student restored:
Roll No: 101
Name: Rahul
Department: CSE

The return; inside the first catch makes the program stop if saving fails, so it never tries to read a file that was not written. Remember: s1 and s2 are two separate objects holding the same data. s2 was rebuilt from bytes.

4.7 I/O versus serialization

Feature I/O (Input/Output) Serialization
Purpose Transfer data Represent and restore object state
Data Bytes, characters, primitives, objects Java object graphs (objects and their references)
Main classes Stream, reader, writer classes (e.g., FileInputStream, BufferedReader) Object streams (ObjectOutputStream, ObjectInputStream)
Needs Serializable? No Normally yes, for serializable classes (implements Serializable)
Example Read student names from a file Save and restore Student objects

Relationship: serialization (object state ↔ byte stream) is built on top of I/O (data transfer using streams). Serialization uses I/O, but not every I/O operation involves serialization.

Supplementary: because serialization saves an object together with the objects it refers to (an object graph), every object reachable from it must itself be serializable. Otherwise, a runtime NotSerializableException occurs.

5. Packages

5.1 The problem and the idea

The problem. A university application will have dozens of classes: students, faculty, courses, exams. Two different programmers may even both write a class called Student. Where do they all go, and how does Java tell them apart?

The analogy. Folders on a computer. Two files named report.txt can live in different folders, and the full path tells them apart. Where the analogy stops: a package is a namespace (a naming scope), not merely a folder, although Java expects the folder structure to match the package name.

A package is a namespace used to group related Java classes, interfaces, enums, records, and other types. Packages organise code, avoid naming conflicts, and control access between classes.

Why use packages?

  • Organise code into meaningful modules.

  • Avoid naming conflicts (e.g., Student in different packages).

  • Control access between classes (using access modifiers).

  • Improve maintainability and reusability.

    The tree shows a university application. The root package university contains the sub-packages students (holding Student.java and StudentService.java), faculty (Faculty.java), courses (Course.java), and exams (Result.java). Directories typically map to package names, so the full package name of the student classes is university.students. Notice how the dots in the name correspond to folder levels. 

university/
├── students/
│   ├── Student.java
│   └── StudentService.java
├── faculty/
│   └── Faculty.java
├── courses/
│   └── Course.java
└── exams/
    └── Result.java

5.2 Defining a package and using a class from it

General pattern:

package packageName;            // first statement of a file in that package

import packageName.ClassName;   // in a file that wants to use that class

Defining (file Student.java inside the university/students folder):

package university.students;

public class Student {
    private int rollNo;
    private String name;
    // ...
}

Using (file UniversityApp.java):

import university.students.Student;

public class UniversityApp {
    public static void main(String[] args) {
        Student s = new Student();
        // ...
    }
}
Keyword Meaning
package Declares which package this file belongs to. It must come before the imports and the class, and a file has at most one.
import Lets you refer to a class from another package by its simple name
public (on the class) Required if code in other packages must use the class

5.3 Types of packages

Java packages are commonly categorised into two types:

  • Built-in packages: provided by the Java platform (e.g., java.lang, java.util).
  • User-defined packages: created by programmers to organise application code (e.g., university.students).
Package Purpose Common classes (examples)
java.lang Core language support String, Math, Object
java.util Utilities and collections Scanner, ArrayList, HashMap
java.io Traditional I/O (input and output) File, FileInputStream, Serializable
java.nio.file Modern file operations (NIO.2) Path, Files
java.net Networking Socket, URL
java.time Date and time APIs LocalDate, LocalDateTime
java.sql Database connectivity APIs (JDBC) Connection, ResultSet

Classes in java.lang are automatically available without an explicit import. This is why String, Math, Object, and Cloneable need no import, whereas Scanner and Serializable do.

5.4 Creating a user-defined package

Goal: put a Student class in a package named mypackage and use it from Main.

Project structure:

(Parent Directory)
├── mypackage/
│   └── Student.java
└── Main.java

The first file declares package mypackage; and makes both the class and its method public, which allows access from another package. Because Main lives in a different package, it must write import mypackage.Student; before it can use Student by its simple name. Remove public from the class or method, and Main can no longer access it. To compile, use javac -d . mypackage/Student.java Main.java; the -d . option tells the compiler to place the class files into directories corresponding to their package names, starting in the current directory. Then run with java Main. 

// File: mypackage/Student.java
package mypackage;

public class Student {
    public void display() {
        System.out.println(
            "Hello from the Student package");
    }
}
// File: Main.java
import mypackage.Student;

public class Main {
    public static void main(String[] args) {
        Student s = new Student();
        s.display();
    }
}

Compile and run:

> javac -d . mypackage/Student.java Main.java
> java Main

Output: Hello from the Student package

Result after compilation: class files are created in a directory structure that matches the package name:

(Parent Directory)
├── mypackage/
│   └── Student.class
└── Main.class

5.5 Importing packages

Java supports different import patterns:

Pattern Example Effect
1. A specific class import java.util.Scanner; Imports only the Scanner class from java.util
2. All accessible types in a package import java.util.*; Imports all accessible (public) types in java.util (e.g., Scanner, ArrayList, HashMap) but does not recursively import subpackages, so not java.util.regex
3. A fully qualified class name java.util.Scanner sc = new java.util.Scanner(System.in); No import needed; the full name is written each time

Note for Review: java.util.regex is a separate package, not a "part" of java.util. The * never reaches into it. To use Pattern, you must import java.util.regex.Pattern (or java.util.regex.*).

5.6 Access modifiers and packages

Java access modifiers determine visibility:

Modifier Same class Same package Subclass in another package Unrelated class in another package
public Yes Yes Yes Yes
protected Yes Yes Yes, with restrictions No
No modifier (package-private) Yes Yes No No
private Yes No No No

For protected, cross-package access through inheritance follows Java's specific qualifying-reference rules; it is not equivalent to unrestricted public access.

Summary: public is accessible from anywhere. protected is accessible within the same package and by subclasses in other packages (with restrictions). No modifier is accessible only within the same package. private is accessible only within the same class.

Program: access modifiers between packages.

// File: college/Student.java
package college;

public class Student {
    public String name = "Rahul";
    private int password = 1234;

    public void display() {
        System.out.println(name);
    }
}
// File: Main.java
import college.Student;

public class Main {
    public static void main(String[] args) {
        Student s = new Student();
        System.out.println(s.name);
        s.display();
        // System.out.println(s.password);
        // INVALID: password has private access (compile-time error)
    }
}

Output:

Rahul
Rahul

s.name is public, so Main may read it. s.display() is public too and prints the same name. The private field password cannot be accessed directly from outside the Student class, even if the accessing class belongs to the same package.

5.7 Static imports

Static imports allow static members to be referenced without explicitly writing the declaring class name.

Normally you must write Math.PI and Math.sqrt(25). With import static java.lang.Math.PI; and import static java.lang.Math.sqrt;, the names PI and sqrt() can be used directly. Note the syntax: the keyword is import static, and it names a specific static member (or * for all of them), not just a class. Static imports bring static fields, methods, or nested types into scope. The area is PI * radius * radius and the square root of 25 is 5.0, as the output shows. 

import static java.lang.Math.PI;
import static java.lang.Math.sqrt;

public class StaticImportDemo {
    public static void main(String[] args) {
        double radius = 5.0;
        double area = PI * radius * radius;
        System.out.println("Area = " + area);
        System.out.println("Square root = " + sqrt(25));
    }
}

Output:

Area = 78.53981633974483
Square root = 5.0

6. Putting It All Together

We now combine all four ideas in one small University Application: packages organise the code, clone() duplicates a student, serialization plus file I/O saves and loads it.

Project structure:

UniversityApplication/
├── university/
│   ├── model/
│   │   └── Student.java
│   └── storage/
│       └── StudentStorage.java
└── Main.java

The workflow starts with an original Student, which is cloned into an independent copy. The cloned student is then serialized into the file studentdata.ser through ObjectOutputStream, and later deserialized with ObjectInputStream into a restored Student. Each concept plays one role: packages organise the model and storage logic, cloning duplicates, serialization converts the object to bytes, and I/O streams move those bytes to and from the file.

6.1 The model: university/model/Student.java

package university.model;

import java.io.Serializable;

public class Student implements Serializable, Cloneable {
    private static final long serialVersionUID = 1L;

    private int rollNo;
    private String name;
    private String department;

    public Student(int rollNo, String name, String department) {
        this.rollNo = rollNo;
        this.name = name;
        this.department = department;
    }

    @Override
    public Student clone() {
        try {
            return (Student) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    public void setName(String name) {
        this.name = name;
    }

    public void display() {
        System.out.println(rollNo + " " + name + " " + department);
    }
}
  • The class implements Serializable (enables object serialization) and Cloneable (enables cloning).
  • The three instance fields are primitives or immutable strings, so a shallow clone is sufficient to give the two student objects independent mutable state.
  • Here clone() handles the checked exception itself with try/catch, so callers need no throws. An overriding method may declare fewer exceptions than the original. Since the class does implement Cloneable, the exception can never really occur. AssertionError signals "this should be impossible" if it ever does.
  • The members are public because Main is in a different package.

6.2 The storage: university/storage/StudentStorage.java

package university.storage;

import university.model.Student;
import java.io.*;

public class StudentStorage {
    public static void save(Student student, String file)
            throws IOException {
        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream(file))) {
            oos.writeObject(student);
        }
    }

    public static Student load(String file)
            throws IOException, ClassNotFoundException {
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream(file))) {
            return (Student) ois.readObject();
        }
    }
}

Both methods are static, so they belong to the class and are called as StudentStorage.save(...) and StudentStorage.load(...) without creating a StudentStorage object. Here throws on the method means "I do not handle this exception; my caller must". save writes a student to a file; load returns a Student from a file.

6.3 The main program: Main.java

import university.model.Student;
import university.storage.StudentStorage;

public class Main {
    public static void main(String[] args) throws Exception {
        Student original = new Student(101, "Rahul", "CSE");
        Student cloned = original.clone();
        cloned.setName("Amit");

        System.out.println("Original:");
        original.display();
        System.out.println("Cloned:");
        cloned.display();

        StudentStorage.save(cloned, "studentdata.ser");
        Student restored = StudentStorage.load("studentdata.ser");
        System.out.println("Restored:");
        restored.display();
    }
}

Compile and run:

> javac -d . university/model/Student.java \
    university/storage/StudentStorage.java Main.java
> java Main

Output:

Original:
101 Rahul CSE
Cloned:
101 Amit CSE
Restored:
101 Amit CSE

Execution trace:

Step Operation Result
1 new Student(101, "Rahul", "CSE") original created
2 original.clone() New object cloned with the same field values
3 cloned.setName("Amit") Only cloned changes; original keeps Rahul
4 Two display() calls 101 Rahul CSE and 101 Amit CSE
5 StudentStorage.save(cloned, ...) cloned serialized into studentdata.ser
6 StudentStorage.load(...) A third object restored rebuilt from the bytes
7 restored.display() 101 Amit CSE: it carries the saved state of cloned

6.4 A second version of the same project

The same project, with a Student made of id, name, and cgpa, appears in this form. StudentStorage is the same as above.

package university.model;

import java.io.Serializable;

public class Student implements Cloneable, Serializable {
    private int id;
    private String name;
    private double cgpa;

    public Student(int id, String name, double cgpa) {
        this.id = id;
        this.name = name;
        this.cgpa = cgpa;
    }

    @Override
    public Student clone() throws CloneNotSupportedException {
        return (Student) super.clone();
    }

    @Override
    public String toString() {
        return "Student[id=" + id + ", name=" + name
                + ", cgpa=" + cgpa + "]";
    }
}
import university.model.Student;
import university.storage.StudentStorage;

public class Main {
    public static void main(String[] args) throws Exception {
        Student s1 = new Student(101, "Ananya", 9.1);
        Student s2 = s1.clone();                               // Cloning
        s2 = new Student(102, "Ananya (Cloned)", 9.1);
        StudentStorage.save(s2, "student.ser");                // Serialization
        Student s3 = StudentStorage.load("student.ser");       // Deserialization

        System.out.println("Original    : " + s1);
        System.out.println("Cloned      : " + s2);
        System.out.println("Deserialized: " + s3);
    }
}

Output:

Original    : Student[id=101, name=Ananya, cgpa=9.1]
Cloned      : Student[id=102, name=Ananya (Cloned), cgpa=9.1]
Deserialized: Student[id=102, name=Ananya (Cloned), cgpa=9.1]

Note for Review (a subtle point): in this version, s2 first receives the clone of s1, but the next line assigns s2 a new Student. The clone is then no longer referenced by anything. Because the fields are private and there is no setter, the example uses a new object to get a visibly different record. The output therefore shows the constructed object being saved and restored, not the clone. The version in Section 6.3, which changes the clone with setName, demonstrates the clone itself. Also, this version omits serialVersionUID; Java will then compute one automatically, but declaring it explicitly is recommended.

Process flow: Student object (s1) → Clone (s2) → Serialize (save to student.ser) → Deserialize (load from student.ser) → Retrieved object (s3).

Key idea of the chapter: Packages organise the classes. Cloning gives you an independent copy in memory. I/O streams move bytes to and from the outside world. Serialization turns an object into bytes so that I/O can carry it, and back again.
