Anatomy of a Java Program

The problem. Before studying any OOP feature, you need a reliable way to type a program, run it, and see the result. An online Java compiler (the lecture uses OneCompiler) gives you an editor on the left and a Console on the right that shows whatever the program prints. Press Run and the output appears.

Every program in this session has the same skeleton: imports → class → main method → statements.

The smallest complete program has four parts. The import line brings in library classes (only needed when you use something outside java.lang, such as Scanner, ArrayList or HashSet). The class holds all the code. main is the entry point where execution begins. The statements inside main do the work; System.out.println(...) prints a line to the console. 

import java.util.Scanner;   // only if needed

public class Main {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
Hello, World!

The File-Name Rule

The class that contains main should be saved in a file with exactly the same name plus .java (a public class Main goes in Main.java; public class EncapsulationDemo goes in EncapsulationDemo.java). Java is case-sensitive here.

In this lab, almost every "error" that appeared came from pasting a new program under an old file name. Habit to build: paste the code, rename the file to the class that has main, then run.

Note for Review: A .java file may contain several classes, but at most one of them can be public, and that one must match the file name.

Encapsulation

The Problem

Imagine a bank-account program where balance is an ordinary public variable. Any line of code anywhere can write account.balance = -5000; and silently corrupt the data. We need a way to protect the data and allow changes only through rules we control.

The Intuitive Idea and the Analogy

A bank keeps cash in a vault. You do not walk in and take it; you talk to a counter clerk who checks the request ("you cannot deposit a negative amount") and then touches the vault on your behalf. The vault is the private data; the clerk is the method.

Where the analogy stops: a real clerk can refuse with an explanation. Our simple setter below just ignores an invalid request, which is a design choice, not a rule of Java.

The Formal Concept

Encapsulation is the object-oriented concept of binding data (variables) and the methods that operate on that data into a single unit, a class, and hiding the data from direct outside access. Outside code can reach the data only through the class's methods.

To check whether a program is encapsulated, ask: does one class hold the data together with the methods that work on it, and is the data hidden?

General Pattern

The standard recipe is: make each field private, then provide a setter (a method to change it, where validation lives) and a getter (a method to read it). The names follow the convention setX and getX. Replace DataType and fieldName with real types and names. 

class ClassName {
    private DataType fieldName;

    public void setFieldName(DataType value) {
        // validate, then assign
    }

    public DataType getFieldName() {
        return fieldName;
    }
}

The Java Implementation

The lecture uses two classes with separate responsibilities: BankAccount holds the data and rules, and EncapsulationDemo is the main class that creates an object and uses it.

Goal: store a balance that can never be set to a negative number. setBalance changes the balance only when the new value is >= 0, and getBalance returns the current value. The driver class creates one BankAccount, sets it to 10000, and prints it. Save this as EncapsulationDemo.java because that is the public class containing main. 

class BankAccount {
    private double balance;

    public void setBalance(double balance) {
        if (balance >= 0) {
            this.balance = balance;
        }
    }

    public double getBalance() {
        return balance;
    }
}

public class EncapsulationDemo {
    public static void main(String[] args) {
        BankAccount account = new BankAccount();
        account.setBalance(10000);
        System.out.println("Balance = "
                + account.getBalance());
    }
}
Balance = 10000.0

Changing the call to account.setBalance(80000); produces Balance = 80000.0. The .0 appears because balance is a double, and a double prints with its decimal part.

The class diagram shows what encapsulation looks like structurally: the minus sign marks the private field, the plus signs mark public methods, and the dashed arrow means EncapsulationDemo creates and uses a BankAccount but never touches balance directly.

Syntax Breakdown

Code What it means
private double balance; A field (belongs to every object). private means only code inside BankAccount may touch it. double holds decimal numbers such as money.
public void setBalance(double balance) A method declaration. public: callable from outside. void: returns nothing. (double balance): one parameter, a local variable that receives the caller's value.
if (balance >= 0) Here balance is the parameter (the new value being offered).
this.balance = balance; this.balance is the field; the right-hand balance is the parameter. this means "the object this method is running on".
public double getBalance() Non-void return type: the method must hand back a double.
return balance; Sends the field's value back to the caller. Nothing is printed here.

Reference, Object and Assignment

BankAccount account = new BankAccount(); is really two actions. The left part declares a reference variable named account that can point to a BankAccount. The right part creates the object with new (Java allocates memory and runs the constructor; since none is written, a default one is supplied) and returns its reference, which = stores in account. The variable holds the address-like reference, not the object itself. 

BankAccount account;            // declare
account = new BankAccount();    // create + assign

Execution Trace

Step Operation Result
1 new BankAccount() Object created; balance starts at default 0.0; account references it
2 account.setBalance(10000) int 10000 widened to double 10000.0; parameter balance = 10000.0
3 if (balance >= 0) 10000.0 >= 0 is true
4 this.balance = balance; The object's field becomes 10000.0
5 account.getBalance() Returns 10000.0
6 println(...) Text is joined and printed: Balance = 10000.0

If the call were account.setBalance(-500);, step 3 would be false, the assignment would be skipped, and the output would be Balance = 0.0 (the default value remains). The condition is only one example of validation; other rules can be added the same way.

Why the Field Must Be Private

Invalid code, labeled clearly: if code outside the class tries to write the field directly, the compiler stops the build. This is a compile-time error, so the program never runs. The message you will see is that balance has private access in BankAccount. Private data forces every change through setBalance, where the rule balance >= 0 is enforced. 

// INVALID: does not compile
BankAccount account = new BankAccount();
account.balance = -5000;

Note for Review: Encapsulation = private data + public methods in one class. The getter returns a value; printing is a separate job done by the caller.

Inheritance

The Problem

Suppose a college payroll has Employee, Manager and Director. All three share a name, an ID and a basic salary calculation. Writing those members three times is wasteful, and a bug fix would need to be repeated in each copy. We want to write shared code once and reuse it.

The Formal Concept

Inheritance is a mechanism where one class acquires the properties (fields) and behaviors (methods) of another class. It is a core pillar of OOP, used for code reusability, and it models an "IS-A" relationship: a Car is a Vehicle.

Term Other names Meaning
Superclass base class, parent class The class being inherited from
Subclass derived class, child class The class that inherits (uses extends)

(The superclass is the parent; the subclass is the child. They are not interchangeable.)

Syntax: extends

A subclass is declared by writing extends and the superclass name after its own name. Everything accessible in the superclass becomes usable through the subclass, and the subclass can add its own members. Java allows only one class after extends. Private members of the superclass are part of the object but cannot be accessed directly by name from the subclass. 

class SuperClassName {
    // fields and methods to share
}

class SubClassName extends SuperClassName {
    // extra fields and methods
}

bruck

Types of Inheritance

Type Meaning Java pattern Supported?
Single One subclass from one superclass class A {} / class B extends A {} Yes
Multilevel A chain: A → B → C class B extends A {} / class C extends B {} Yes
Hierarchical One superclass, several subclasses class B extends A {} / class C extends A {} Yes
Multiple One subclass with several superclasses class C extends A, B {} No

The arrows below point from the subclass up to the superclass.

Single inheritance: class B inherits from class A only. B can use A's accessible members plus its own.

Multilevel inheritance: a linear chain. B inherits from A, and C inherits from B, so C also gets what B received from A.

Hierarchical inheritance: one parent distributes its common members to several separate children, forming a tree. B and C are siblings and know nothing about each other.

Multiple inheritance (not allowed for classes): class C would inherit from two classes at once. Java does not support this, so extends A, B is a compile-time error. A classic reason is ambiguity: if A and B both defined the same method, C could not know which one to inherit. (Interfaces provide a safe alternative, covered later.)

Invalid code, labeled clearly: this is the form the lecture marks as unsupported. The compiler rejects the comma after A. 

class A { }
class B { }

// INVALID: Java does not support multiple inheritance
class C extends A, B { }

So Java supports three inheritance types for classes: single, multilevel and hierarchical.

Example 1: Single Inheritance

Goal: Dog reuses the eat() method written once in Animal, and adds its own bark().

Animal is the superclass with one method, eat(). Dog extends Animal, so a Dog object has eat() without redefining it, plus its own bark(). The class containing main is Dog, so the file is Dog.java. Notice that d.eat() is code reuse: no eat method exists in Dog. 

class Animal {
    void eat() {
        System.out.println("Animal eats");
    }
}

class Dog extends Animal {
    void bark() {
        System.out.println("Dog barks");
    }

    public static void main(String[] args) {
        Dog d = new Dog();
        d.eat();    // inherited from Animal
        d.bark();   // defined in Dog
    }
}

Goal: Circle and Square both reuse a common message() from Shape.

Shape is the base class with message(). Both Circle and Square extend it and add one method each. The main class HierarchicalDemo creates one object of each. Each object can call the shared message() plus its own method, which is why "This is a shape" prints before each shape name. Save as HierarchicalDemo.java.

Note for Review: Single = one child. Multilevel = a vertical chain. Hierarchical = many children of one parent. The reusable idea is the same each time: define once in the superclass, use everywhere below it.

Polymorphism

The Problem

A billing program needs an area function. A square needs one number (its side); a rectangle needs two (length and breadth). Inventing areaSquare, areaRectangle, and so on makes the program clumsy. Similarly, a checkout screen should say "pay" without caring whether payment is by card or UPI.

The Formal Concept

Polymorphism means "many forms": the same method name can behave differently. Java achieves it in two ways.

Aspect Compile-time polymorphism Runtime polymorphism
Also called static polymorphism, early binding dynamic polymorphism, dynamic dispatch
Achieved by Method overloading Method overriding
Where Several methods in the same class Same method in a superclass and subclass
Decided by The compiler, from the argument list The JVM, from the actual object at run time

Compile-Time Polymorphism: Method Overloading

Overloading: several methods in one class share a name but have different parameter lists (different number, types or order of parameters). The compiler resolves which one to call while compiling.

Goal:** compute the area of a square from one value, or of a rectangle from two. Both methods are named calculate. calculate(5) matches the one-parameter version; calculate(4, 5) matches the two-parameter version. The methods return the result and main prints it. Save as Area.java. 

class Area {
    int calculate(int side) {
        return side * side;
    }

    int calculate(int length, int breadth) {
        return length * breadth;
    }

    public static void main(String[] args) {
        Area area = new Area();
        System.out.println(area.calculate(5));
        System.out.println(area.calculate(4, 5));
    }
}
25
20

The arithmetic: square area =side2=52=25, and rectangle area =length×breadth=4×5=20.

Call Arguments Method chosen Result
area.calculate(5) one int calculate(int side) 5×5=25
area.calculate(4, 5) two ints calculate(int length, int breadth) 4×5=20

Invalid code, labeled clearly: the return type alone cannot distinguish overloaded methods. These two have the same name and the same parameter types, so the compiler reports that the method is already defined in the class. A parameter's name does not count either; only the types, number and order do. 

class Area {
    // INVALID: same name, same parameters
    int calculate(int side) { return side * side; }
    double calculate(int radius) { return radius * 3.14; }
}

Method Overriding

Overriding: a subclass supplies its own version of a method it inherited, using the same name and the same parameters. When called on a subclass object, the subclass version replaces the parent's.

Parent and Child both define display(). Child overrides it, so a Child object runs its own version. The @Override annotation is optional but valuable: it asks the compiler to confirm that a parent method with that exact signature really exists. If you mistype the name (displya), compilation fails instead of silently creating a new unrelated method. Save as Child.java. 

class Parent {
    void display() {
        System.out.println("Parent Method");
    }
}

class Child extends Parent {
    @Override
    void display() {
        System.out.println("Child Method");
    }

    public static void main(String[] args) {
        Child c = new Child();
        c.display();
    }
}
Child Method

Why Child Method and not Parent Method? The object is a Child. Java starts searching in Child, finds display() there, and never reaches the parent's version.

Overloading Overriding
Classes One class Parent and child
Parameters Must differ Must be the same
Resolved Compile time Run time
Purpose Same action, different inputs Replace inherited behavior

The super Keyword (Self-Practice Topic)

this refers to the current object; super refers to the parent part of the current object. Writing super.display() inside an overriding method runs the parent's version first, so you extend the behavior instead of fully replacing it. (super(...) can also call a parent constructor, used inside a subclass constructor.) 

class Parent {
    void display() {
        System.out.println("Parent Method");
    }
}

class Child extends Parent {
    @Override
    void display() {
        super.display();
        System.out.println("Child Method");
    }

    public static void main(String[] args) {
        new Child().display();
    }
}

Runtime Polymorphism: Dynamic Dispatch

The problem. A payment screen must call pay() without knowing in advance whether the customer chose a credit card or UPI. The parent type Payment is used as the variable type; the real object decides which pay() runs.

Payment has a general pay(). CreditCard and UPI both override it. In main, one variable p of type Payment first points to a CreditCard object and later to a UPI object. The same statement p.pay() prints different text, because Java picks the method from the object's actual class when the line runs. Save as DynamicDispatchDemo.java. 

class Payment {
    void pay() {
        System.out.println("General Payment");
    }
}

class CreditCard extends Payment {
    @Override
    void pay() {
        System.out.println(
            "Payment using Credit Card");
    }
}

class UPI extends Payment {
    @Override
    void pay() {
        System.out.println("Payment using UPI");
    }
}

public class DynamicDispatchDemo {
    public static void main(String[] args) {
        Payment p;

        p = new CreditCard();
        p.pay();

        p = new UPI();
        p.pay();
    }
}
Payment using Credit Card
Payment using UPI

The diagram shows the relationship: both payment methods are subclasses of Payment and each overrides pay(). The general pay() in Payment would run only if the object were a plain Payment.

Compile-time type versus runtime object type. The variable's declared type is Payment (compile-time type): the compiler only checks that Payment has a pay() method. The object's real class is CreditCard or UPI (runtime type): the JVM uses it to select the version.

Step Statement Variable type Object type Method that runs Output
1 p = new CreditCard(); Payment CreditCard — —
2 p.pay(); Payment CreditCard CreditCard.pay() Payment using Credit Card
3 p = new UPI(); Payment UPI — —
4 p.pay(); Payment UPI UPI.pay() Payment using UPI

Note for Review: Because the choice is made while the program runs, a new payment type (say NetBanking extends Payment) can be added later and a method that accepts a Payment will work with it unchanged.

Abstract Classes

The Problem

Every shape must be able to report its area, but a general "shape" has no formula; only a circle, square or triangle does. We want a parent class that forces every child to supply area() without pretending to implement it itself.

The Formal Concept

An abstract class is a restricted class declared with the abstract keyword. It cannot be instantiated directly (you cannot create an object of it). It serves as a template or blueprint for other classes and can define behavior common to them.

Syntax

Put abstract before class to make a class abstract. An abstract method has the keyword abstract, a return type and a name, but no body, only a semicolon. Any non-abstract subclass must override every abstract method, or the subclass must itself be declared abstract. An abstract class may also contain ordinary methods and fields. 

abstract class ClassName {
    abstract returnType methodName();   // no body
}

Implementation

Goal: compute the area of a circle of radius 5. ShapeAbstract declares the rule that area() must exist; CircleAbstract overrides it with the formula πr2 using Math.PI. The variable s has the abstract type, but the object is a concrete CircleAbstract; this is allowed and uses runtime polymorphism. Save as CircleAbstract.java. 

abstract class ShapeAbstract {
    abstract void area();
}

class CircleAbstract extends ShapeAbstract {
    double radius = 5;

    @Override
    void area() {
        double result =
            Math.PI * radius * radius;
        System.out.println("Area = " + result);
    }

    public static void main(String[] args) {
        ShapeAbstract s = new CircleAbstract();
        s.area();
    }
}

Interfaces

The Problem

Several unrelated classes (a Report, an Invoice, a Photo) can all be printed. They share no parent, yet we want a guarantee that anything labeled "printable" has a print() method.

The Formal Concept

An interface acts as a blueprint of a class: it specifies what a class must do, but not how. It is the main tool for achieving abstraction and for the effect of multiple inheritance in Java.

Syntax

An interface lists method signatures. A class signs the contract with implements and must provide a body for every method. Methods in an interface are automatically public, so the implementing method must also be declared public (writing it without public is a compile-time error about weaker access). A class may implement several interfaces, separated by commas. 

interface Printable {
    void print();
}

class Report implements Printable {
    @Override
    public void print() {
        System.out.println("Printing report");
    }

    public static void main(String[] args) {
        Printable item = new Report();
        item.print();
    }
}
Printing report

The method bodies and message text here are illustrative; the lecture's example is a Printable interface implemented by a Report class whose main creates the object and prints the result. The file is saved as Report.java.

Invalid code, labeled clearly: an interface has no implementation, so it cannot be created with new (the lecture's attempt to create an object directly from the interface fails for this reason, apart from the online compiler's own file-name issues). Create an object of an implementing class and store it in an interface-typed variable. 

// INVALID: interface cannot be instantiated
Printable item = new Printable();

Multiple Interfaces (Self-Practice Topic)

A class can only extend one class, but it can implement many interfaces. OfficeMachine promises both abilities and must therefore supply both methods. This is how Java gets the benefit of multiple inheritance without the ambiguity problem of inheriting implementation from two classes. 

interface Printable { void print(); }
interface Scannable { void scan(); }

class OfficeMachine
        implements Printable, Scannable {
    public void print() {
        System.out.println("Printing");
    }
    public void scan() {
        System.out.println("Scanning");
    }
}

The dashed hollow arrow means "implements". Compare it with the solid hollow arrow used earlier for extends.

Exception Handling

The Problem

A marks-processing program divides a total by a number of subjects. If a user enters 0, the program crashes and everything after that line is lost. An exception is an abnormal condition that disrupts normal execution at run time. Exception handling is the mechanism that lets the program respond and continue gracefully.

Syntax: try and catch

Put risky code in the try block. If an exception of the stated type occurs, Java immediately jumps to the matching catch block and skips the rest of try. An optional finally block runs in every case, whether or not an exception happened. A try needs at least one catch or a finally. In catch (ExceptionType e), e is a variable that holds the exception object. 

try {
    // code that might fail
} catch (ExceptionType e) {
    // what to do when it fails
} finally {
    // optional: always runs
}

Example 1: Division by Zero

Integer division by zero throws an ArithmeticException. The println(result) line is never reached, because control jumps to the catch block at the moment the exception occurs. The program then ends normally instead of crashing. Save as ArithmeticDemo.java. 

public class ArithmeticDemo {
    public static void main(String[] args) {
        try {
            int result = 10 / 0;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println(
                "Cannot divide by zero");
        }
    }
}
Cannot divide by zero

(Dividing a double by zero, such as 10.0 / 0, does not throw; it yields Infinity. The exception is specific to integer division.)

Example 2: Array Index Out of Bounds

The array has three elements, so the only valid indexes are 0, 1 and 2. The statement numbers[5] asks for a position that does not exist, which throws ArrayIndexOutOfBoundsException; the catch prints a friendly message. Save as ArrayExceptionDemo.java. 

public class ArrayExceptionDemo {
    public static void main(String[] args) {
        int[] numbers = {10, 20, 30};

        try {
            System.out.println(numbers[5]);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println(
                "Invalid array index");
        }
    }
}
Invalid array index

Index 0 1 2 5
Value 10 20 30 does not exist

Index counting starts at 0, so numbers[5] is the sixth position, not the fifth. Either way it lies beyond the last valid index, numbers.length - 1 = 2.

Note for Review: If the output panel still shows text from an earlier program (for example "Cannot divide by zero" after running the array program), the file was not re-run. Run again and read the newest output.

Multiple catch Blocks and finally (Self-Practice Topic)

One try can have several catch blocks, tried top to bottom; the first matching one runs. The general Exception must be last, since it matches everything, and placing it first makes later blocks unreachable (a compile-time error). Here the array access fails first, so Invalid index prints, the division line is skipped, and finally still runs.

try {
    int[] marks = {80, 90};
    System.out.println(marks[2]);
    System.out.println(10 / 0);
} catch (ArithmeticException e) {
    System.out.println("Arithmetic problem");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Invalid index");
} catch (Exception e) {
    System.out.println("Other problem");
} finally {
    System.out.println("Always runs");
}

throw, throws and User-Defined Exceptions (Self-Practice Topic)

You can create your own exception type by extending Exception, pass a message up with super(message), and signal a problem with throw.

InvalidMarksException extends Exception is the custom type; its constructor passes the message to the parent with super(message). checkMarks declares that it may fail using throws, and actually raises the problem with throw new .... The caller must handle it with try/catch. The first call is valid; the second throws, so the catch prints the stored message. 

class InvalidMarksException extends Exception {
    InvalidMarksException(String message) {
        super(message);
    }
}

public class MarksDemo {
    static void checkMarks(int marks)
            throws InvalidMarksException {
        if (marks < 0 || marks > 100) {
            throw new InvalidMarksException(
                "Marks must be 0 to 100");
        }
        System.out.println("Valid marks: " + marks);
    }

    public static void main(String[] args) {
        try {
            checkMarks(85);
            checkMarks(120);
        } catch (InvalidMarksException e) {
            System.out.println(

Collections

The Problem

An array has a fixed size. A class-roster program needs a list that grows and shrinks as students are added or removed. Java's Collections framework provides ready-made classes for this, and generics (the <String> in ArrayList<String>) state what type of elements the collection may hold so mistakes are caught at compile time.

Structure Key behavior
ArrayList Ordered, allows duplicates, access by index
LinkedList Ordered list; also usable as a queue
HashSet No duplicates, no guaranteed order
TreeSet No duplicates, kept in sorted order
Queue (e.g. LinkedList) First In, First Out (FIFO)
PriorityQueue Smallest element is served first
HashMap Stores key → value pairs

Only the relationships the lecture uses are drawn. List, Set and Queue are kinds of Collection; the concrete classes implement them. LinkedList implements both List and Queue. HashMap belongs to the separate Map family, since it stores pairs rather than single elements.

ArrayList

Goal: keep a growing list of student names, read one, remove one, and count the rest.

import java.util.ArrayList; makes the class available. ArrayList<String> students = new ArrayList<>(); declares a list of strings; the empty <> lets Java infer the type. add appends, get(0) reads the first element (indexes start at 0), remove("Rahul") deletes the first element equal to that text, and size() counts the elements. Save as ArrayListDemo.java. 

import java.util.ArrayList;

public class ArrayListDemo {
    public static void main(String[] args) {
        ArrayList<String> students =
            new ArrayList<>();

        students.add("Amit");
        students.add("Neha");
        students.add("Rahul");
        students.add("Amit");

        System.out.println("Students: " + students);
        System.out.println("First Student: "
            + students.get(0));

        students.remove("Rahul");

        System.out.println("After Removal: "
            + students);
        System.out.println("Total Students: "
            + students.size());
    }
}
Students: [Amit, Neha, Rahul, Amit]
First Student: Amit
After Removal: [Amit, Neha, Amit]
Total Students: 3
Step Operation List after the step
1 four add(...) calls [Amit, Neha, Rahul, Amit] (duplicate Amit is allowed)
2 get(0) unchanged; returns Amit
3 remove("Rahul") [Amit, Neha, Amit]
4 size() unchanged; returns 3

Note for Review: get(10) on a three-element list would throw an IndexOutOfBoundsException, the same family of problem as the array example. The same pattern works with LinkedList.

HashSet: No Duplicates

The ArrayList above stored Amit twice. A set is used when each item must appear only once.

Four add calls are made, but "Java" is added twice. The second add("Java") is ignored because it is already present, so the size is 3. contains("Java") checks membership and returns true. The printing order of a HashSet is not guaranteed; the order shown is just what the run produced. Save as HashDemo.java. 

import java.util.HashSet;

public class HashDemo {
    public static void main(String[] args) {
        HashSet<String> languages =
            new HashSet<>();

        languages.add("Java");
        languages.add("C++");
        languages.add("Python");
        languages.add("Java");   // ignored

        System.out.println("Languages: "
            + languages);
        System.out.println("Contains Java: "
            + languages.contains("Java"));
        System.out.println("Size: "
            + languages.size());
    }
}
Languages: [Java, C++, Python]
Contains Java: true
Size: 3

Queue: First In, First Out

Analogy: a ticket counter line. The person who arrived first is served first.

A Queue is declared with the interface type and created with LinkedList, which implements it; both need an import. add joins the back of the line. peek() looks at the front without removing it. remove() removes the front element. Because the queue is FIFO, Task-1 (added first) is the one removed. Save as QueueDemo.java. 

import java.util.LinkedList;
import java.util.Queue;

public class QueueDemo {
    public static void main(String[] args) {
        Queue<String> queue = new LinkedList<>();

        queue.add("Task-1");
        queue.add("Task-2");
        queue.add("Task-3");

        System.out.println("Queue: " + queue);
        System.out.println("Front Element: "
            + queue.peek());

        queue.remove();

        System.out.println("After Removal: "
            + queue);
    }
}
Queue: [Task-1, Task-2, Task-3]
Front Element: Task-1
After Removal: [Task-2, Task-3]
Step Operation Queue (front → back)
1 three add(...) Task-1, Task-2, Task-3
2 peek() unchanged; returns Task-1
3 remove() Task-2, Task-3

PriorityQueue

A priority queue does not serve in arrival order; it always serves the smallest element first.

Four numbers are added in mixed order. peek() returns the smallest value, 10, regardless of insertion order, and isEmpty() reports whether any elements remain. The values here are illustrative. Printing the whole queue shows its internal arrangement, which is not guaranteed to be sorted; only peek() and removal reliably give the smallest element. 

import java.util.PriorityQueue;

public class PriorityQueueDemo {
    public static void main(String[] args) {
        PriorityQueue<Integer> numbers =
            new PriorityQueue<>();

        numbers.add(40);
        numbers.add(10);
        numbers.add(30);
        numbers.add(20);

        System.out.println("Smallest: "
            + numbers.peek());
        System.out.println("Is empty: "
            + numbers.isEmpty());
        System.out.println("Queue: " + numbers);
    }
}
Smallest: 10
Is empty: false
Queue: [10, 20, 30, 40]

HashMap (Brief)

A HashMap stores key → value pairs and looks values up by key. put adds or replaces a pair and get returns the value for a key. Here the key is a student's name and the value is a mark. Keys must be unique; values may repeat. 

import java.util.HashMap;

HashMap<String, Integer> marks =
    new HashMap<>();
marks.put("Amit", 85);
marks.put("Neha", 92);
System.out.println(marks.get("Neha"));   // 92

Online Compiler Troubleshooting

Most problems during the lab came from the tool, not the logic. Online compilers are convenient but sometimes behave unexpectedly, which is their main drawback; if code looks correct but will not run, try another compiler or a local setup.

Symptom Likely cause Fix
Error mentioning the class or file name; "could not find or load main class" File name does not match the class containing main Rename the file tab to the exact class name, then run
"reached end of file while parsing" A closing brace } is missing or extra after copy-paste Compare braces; remove or add the missing one
Strange errors on lines that look fine Stray space, comma or extra character introduced while copying Retype the suspicious line
"cannot find symbol" for ArrayList, Queue, etc. Missing import java.util...; Add the import
Output looks wrong or unrelated Console still shows the previous run Run again and read the newest output
Correct code fails only online Platform limitation Test in another compiler or locally
