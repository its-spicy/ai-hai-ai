1. The Big Picture

Java gives us several mechanisms for managing objects, organizing programs, reading and writing data, and preserving object state. Four of them are the focus of this chapter:

  1. Object cloning — creating copies of objects.
  2. Input/Output (I/O) — reading and writing data.
  3. Serialization — converting an object's state into bytes.
  4. Packages — organizing related classes.

These concepts are essential for real applications such as banking systems, student management software, distributed applications, file management systems, and network-based services.

Analogy — the university office. Cloning is the photocopier (a duplicate of a student's record). I/O is the clerk who reads from and writes to the filing cabinet. Serialization is vacuum-packing a record so it can be stored in a drawer or posted to another office. Packages are the departments and folders that keep everything findable.

Concept Main purpose Example application
Cloning Creating copies of objects Duplicating student records
I/O Reading and writing data Reading files and console input
Serialization Converting object state into bytes Saving an employee object to a file
Packages Organizing related classes Grouping classes such as com.university

When do I use which? Copying an object → cloning. Reading or writing from the console, a file or a network → I/O. Turning an object into bytes or a file → serialization. Grouping related classes → packages.

2. Object Cloning

2.1 The Problem: Copying a Student Record

A student management application stores a Student object. An administrator wants a duplicate of that record, to experiment with or edit, without touching the original.

The obvious attempt does not work:

An assignment such as s2 = s1 copies only the reference (the address), not the object. Afterwards, both variables point to the same object, like two keys to the same locker. Changing the object through s2 also changes what s1 sees.

A clone is different: it creates a new object with its own identity whose field values are copied from the original. That is a photocopy, not a second key.

Student s2 = s1;          // alias: ONE object,
                          // two references
Student s3 = s1.clone();  // copy: TWO objects,
                          // equal field values

Formal definition: Object cloning is the process of creating a new object whose field values are copied from an existing object.

In Java, cloning can be performed with the clone() method provided by the Object class. Copy constructors and factory methods are often preferred in modern application design (both are discussed later).

2.2 General Syntax and What Each Part Means

ClassName obj2 = (ClassName) obj1.clone();
Part Meaning
ClassName obj2 Declares a reference variable obj2 that can hold a ClassName object
obj1.clone() Method call on the existing object obj1; it builds and returns a new object
(ClassName) A cast: Object.clone() returns type Object, so we narrow it to the real class
= Stores the returned reference in obj2

The cloned object is a separate object (obj1 == obj2 is false), but its internal references may still point to the same objects as the original. This is the heart of the shallow-versus-deep issue in Section 2.6.

Note for Review: The cast is unnecessary when your class overrides clone() with its own return type, e.g. public Student clone(). Then Student s2 = s1.clone(); compiles directly, as in the lecture examples.

2.3 Why Do We Need Cloning?

Cloning is useful when we want to:

  • Create a copy of an object without modifying the original.
  • Preserve an object's state before performing operations.
  • Duplicate configuration objects or application data.
  • Implement simulations and independent object processing.
  • Avoid manually copying numerous fields.

Banking example. Before simulating a transaction, copy the account's state. The simulation works on the copy, and the real account stays unchanged. (Supplementary sketch below; it uses the Cloneable mechanism explained next.)

class BankAccount implements Cloneable {
    private double balance;

    BankAccount(double balance) { this.balance = balance; }
    void withdraw(double amount) { balance -= amount; }
    double getBalance() { return balance; }

    @Override
    public BankAccount clone() throws CloneNotSupportedException {
        return (BankAccount) super.clone();
    }
}
BankAccount real = new BankAccount(5000);
BankAccount trial = real.clone();     // copy before simulating
trial.withdraw(1200);
System.out.println(real.getBalance());   // 5000.0
System.out.println(trial.getBalance());  // 3800.0

The trial balance is 5000−1200=3800, while the real account is untouched.

2.4 The Cloneable Interface

Java provides the Cloneable marker interface in the java.lang package (so no import is needed). A marker interface declares no methods; it simply signals that the class permits field-by-field cloning through Object.clone().

Rules to remember:

  • Cloneable is a marker interface.
  • Object.clone() is protected, so a class generally exposes its own public clone() method.
  • Calling Object.clone() on an object whose class does not implement Cloneable normally throws CloneNotSupportedException.
  • The default cloning operation copies primitive values and references, but does not recursively clone referenced objects.

CloneNotSupportedException is a checked exception, so the method calling super.clone() must declare throws or use try/catch.

class ClassName implements Cloneable {

    @Override
    public ClassName clone()
            throws CloneNotSupportedException {
        return (ClassName) super.clone();
    }
}
Piece of the pattern Why it is there
implements Cloneable Gives permission; without it super.clone() fails at runtime
public Makes clone() callable from other classes (it is protected in Object; an override cannot be less visible)
ClassName as return type Allowed because an override may return a more specific type; callers need no cast
throws CloneNotSupportedException Object.clone() declares it, so callers must handle it
super.clone() Asks Object to build the field-by-field copy
(ClassName) super.clone() returns Object; we cast it back

Invalid-at-runtime example (do not copy):

// This compiles, but s1.clone() throws CloneNotSupportedException
// at run time, because Student does NOT implement Cloneable.
class Student {
    int rollNo;
    public Student clone() throws CloneNotSupportedException {
        return (Student) super.clone();
    }
}

2.5 Example: Cloning a Student Object

Goal: create s1, clone it into s2, display both, and show that they are different objects with the same data.

class Student implements Cloneable {
    int rollNo;
    String name;

    Student(int rollNo, String name) {
        this.rollNo = rollNo;
        this.name = name;
    }

    @Override
    public Student clone() throws CloneNotSupportedException {
        return (Student) super.clone();
    }

    void display() {
        System.out.println(rollNo + " " + name);
    }
}

public class CloningExample {
    public static void main(String[] args)
            throws CloneNotSupportedException {
        Student s1 = new Student(101, "Rahul");

        Student s2 = s1.clone();

        System.out.println("Original Object:");
        s1.display();
        System.out.println("Cloned Object:");
        s2.display();

        System.out.println(s1 == s2);
    }
}

Output

Original Object:
101 Rahul
Cloned Object:
101 Rahul
false

Syntax breakdown

  • this.rollNo = rollNo; — this.rollNo is the field; the bare rollNo is the constructor parameter. this separates them.
  • @Override — asks the compiler to verify that we really override a superclass method.
  • main(...) throws CloneNotSupportedException — required because clone() declares that checked exception and main does not catch it.
  • s1 == s2 — compares references (are they the same object?), not field values. For content comparison, one would use .equals().

Execution trace

Step Operation Result
1 new Student(101, "Rahul") Constructor runs; s1 refers to the new object
2 s1.clone() Object.clone() creates a new Student with the same field values
3 Assign to s2 s2 refers to the new object (new identity)
4 s1.display() / s2.display() Both print 101 Rahul
5 s1 == s2 Different references, so false

Note for Review: The class implements Cloneable, clone() creates a copy, s1 and s2 hold the same data, and s1 == s2 is false because they are different objects with different memory references. Cloning does not call a constructor for the new object.

2.6 Types of Cloning: Shallow Copy and Deep Copy

Two major types of copying are discussed in Java:

  • Shallow copy: a new outer object is created, but references to nested objects are copied, so both objects share the same nested object.
  • Deep copy: the outer object and its nested mutable objects are copied, giving independent nested objects.

Shallow cloning in action. Employee contains a nested Address object. After e2 = e1.clone(), there are two Employee objects but only one Address. Changing the city through e2 therefore also changes what e1 sees.

Shallow clone program

class Address {
    String city;
    Address(String city) { this.city = city; }
}

class Employee implements Cloneable {
    String name;
    Address address;

    Employee(String name, Address address) {
        this.name = name;
        this.address = address;
    }

    public Employee clone() throws CloneNotSupportedException {
        return (Employee) super.clone();
    }
}

public class ShallowCloneDemo {
    public static void main(String[] args)
            throws CloneNotSupportedException {
        Employee e1 = new Employee("Amit", new Address("Delhi"));
        Employee e2 = e1.clone();

        e2.address.city = "Mumbai";

        System.out.println(e1.address.city);
        System.out.println(e2.address.city);
    }
}

Output

Mumbai
Mumbai
Step Operation Result
1 Create e1 e1.name is "Amit"; e1.address refers to an Address with city "Delhi"
2 e1.clone() New Employee e2; its name and address references are copied
3 e2.address.city = "Mumbai" Follow e2.address to the shared Address and change city
4 Print e1.address.city Mumbai (same Address object)
5 Print e2.address.city Mumbai

e1 and e2 are separate Employee objects, but the Address is shared, so changing it through e2 affects e1 as well. This is a shallow copy, and for mutable nested objects it is usually not what we want.

Deep cloning fixes this. In clone(), after super.clone() creates the shallow copy, we replace the copy's address with a brand-new Address built from the original's data. Now each Employee owns its own Address.

Deep clone: only Employee.clone() changes

@Override
public Employee clone() throws CloneNotSupportedException {
    Employee copy = (Employee) super.clone();            // shallow copy
    copy.address = new Address(this.address.city);       // own Address
    return copy;
}

The Address class, the main method and the rest of the program stay as in the shallow example.

Output of the same main

Delhi
Mumbai

copy.address = new Address(this.address.city); makes the nested object separate: e1 keeps Delhi, and only e2 becomes Mumbai.

Feature Shallow copy Deep copy
Outer object New object New object
Nested mutable object Shared Copied (new object)
Change nested data via the clone Affects the original Does not affect the original
Effort super.clone() only Extra code to copy nested objects

Note for Review: In the deep example, city is a String. Strings are immutable, so sharing the String value is safe; what must not be shared is the mutable Address object. If Address itself contained another mutable object, that object would also need copying for a truly deep clone (supplementary).

2.7 The Copy Constructor

A copy constructor is a constructor that creates a new object by copying the state (data member values) of an existing object of the same class.

Pattern: a constructor whose single parameter has the same type as the class.

class Student {
    int rollNo;
    String name;

    // Parameterized constructor
    Student(int rollNo, String name) {
        this.rollNo = rollNo;
        this.name = name;
    }

    // Copy constructor
    Student(Student other) {
        this.rollNo = other.rollNo;
        this.name = other.name;
    }
}

public class CopyConstructorDemo {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul");
        Student s2 = new Student(s1);       // uses the copy constructor

        System.out.println(s2.rollNo);
        System.out.println(s2.name);
    }
}

Output

101
Rahul

Student has two constructors: the parameterized one initializes a new object from raw values, and the copy constructor copies data from another Student. Java chooses between them by the argument types (int, String versus Student). s1 and s2 hold the same values but are separate objects.

Aspect clone() Copy constructor
Needs Cloneable Yes No
Checked exception to handle Yes (CloneNotSupportedException) No
Created with obj.clone() new ClassName(obj)
Depth of copy Shallow by default Whatever you write (shallow or deep)
Common in modern design Less often Preferred (along with factory methods)

Note for Review (supplementary): A factory method is a static method that returns a new object, e.g. static Student copyOf(Student other). Like a copy constructor, it avoids Cloneable.

Mistake Consequence
Forgetting implements Cloneable CloneNotSupportedException at run time

Shallow-cloning an object with mutable nested objects Changes leak between original and copy

3. Input and Output in Java

3.1 The Problem and the Idea

A program's variables disappear when it ends, and a program that cannot receive data or show results is not very useful. We need a way to bring data in (keyboard, file, network) and send results out (console, file, network).

Input/Output (I/O) is the mechanism through which a program receives information from external sources and sends information to external destinations.

  • Input: reading data from a keyboard, file, network connection, or another source.
  • Output: writing data to the console, file, network connection, or another destination.

Analogy: data flows through a pipe called a stream. The program sits in the middle; input streams bring water in, output streams carry it out.

Java provides I/O classes through several packages:

Package Role
java.io Traditional stream-based I/O
java.nio Buffers, channels and related APIs
java.nio.file File-system operations
java.util Utilities such as Scanner

Data flows through input and output streams.

3.2 Streams in Java

Java I/O streams can be categorized into: byte streams, character streams, buffered streams, data streams, and object streams. The lecture works through byte streams in detail; the other categories use the same ideas with different stream classes.

Category Works with Typical classes
Byte streams Raw 8-bit bytes InputStream, OutputStream, FileInputStream, FileOutputStream
Character streams (supplementary) Text characters Reader, Writer families
Buffered streams Adds a memory buffer for efficiency BufferedInputStream, BufferedOutputStream (and BufferedReader for text)
Data streams Primitive values DataInputStream, DataOutputStream
Object streams Whole objects (serialization) ObjectInputStream, ObjectOutputStream

3.3 Byte Streams

Byte streams operate on bytes (8-bit data) and are useful for binary files such as images, audio files, and executable data.

Use case Example file types
Images .jpg, .png
Audio .mp3, .wav
Video .mp4, .avi
Executable files .exe, .class

The two abstract base classes are InputStream (reading bytes) and OutputStream (writing bytes). Concrete classes extend them:

Input classes (extend InputStream) Output classes (extend OutputStream)
FileInputStream FileOutputStream
BufferedInputStream BufferedOutputStream
DataInputStream DataOutputStream
ObjectInputStream ObjectOutputStream

Key takeaways: byte streams work at the byte level; use InputStream for reading and OutputStream for writing; they provide low-level, efficient I/O; they suit binary data (images, audio, executables, serialized objects).

3.4 Writing Data with FileOutputStream

FileOutputStream is a byte stream class in java.io used to write data (as bytes) to a file.

Goal: write the message Welcome to Java Programming into data.txt.

import java.io.FileOutputStream;
import java.io.IOException;
import java.nio.charset.StandardCharsets;

public class WriteFileDemo {
    public static void main(String[] args) {
        String message = "Welcome to Java Programming";

        try (FileOutputStream fos = new FileOutputStream("data.txt")) {
            byte[] data = message.getBytes(StandardCharsets.UTF_8);
            fos.write(data);
            System.out.println("File written successfully");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Output (console): File written successfully. Result (data.txt): Welcome to Java Programming.

Key steps

  1. Create a FileOutputStream for "data.txt".
  2. Convert the string to a byte array with getBytes(StandardCharsets.UTF_8). Streams carry bytes, not Strings.
  3. Write the byte array with fos.write(data).
  4. The try-with-resources block closes the stream automatically after writing.

Syntax pattern: try-with-resources

try (ResourceType name = new ResourceType(...)) {
    // use the resource
} catch (ExceptionType e) {
    // handle the problem
}
Part Meaning
try ( ... ) Parentheses hold the resource to open; it must be closable
{ ... } Code that uses the resource
Automatic close() Happens when the block ends, even if an exception occurs
catch (IOException e) Handles failures such as a bad path or no permission (IOException is checked)

Note for Review (supplementary): new FileOutputStream("data.txt") creates the file if it does not exist and overwrites it if it does. A relative name like "data.txt" is resolved against the program's working directory.

3.5 Reading Data with FileInputStream

Goal: read data.txt byte by byte and print it.

import java.io.FileInputStream;
import java.io.IOException;

public class ReadFileDemo {
    public static void main(String[] args) {
        try (FileInputStream fis = new FileInputStream("data.txt")) {
            int data;
            while ((data = fis.read()) != -1) {
                System.out.print((char) data);
            }
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Example execution. If data.txt contains the lines Hello Java!, FileInputStream, Demo., the console shows exactly those lines.

How it works

  1. Create a FileInputStream to read bytes from data.txt.
  2. Read one byte at a time with read().
  3. Convert each byte to a character with (char) data.
  4. Stop when the end of the file (-1) is reached.
Construct Explanation
int data; Holds the value returned by read()
(data = fis.read()) != -1 Assigns and tests in one expression: read a byte, store it, compare with -1
read() Returns an int from 0 to 255, or -1 at end of file
(char) data Converts the byte value into a character so it prints as text

read() returns int, not byte, because a byte is signed (-128 to 127); an actual data byte of value 255 would otherwise look like -1.

Note for Review (supplementary): (char) data is fine for plain ASCII text, as in this example. Multi-byte UTF-8 characters would be broken apart, which is why text is normally read with character streams.

3.6 Common I/O Mistakes

Mistake Consequence
Not handling IOException Compile-time error (checked exception)
Treating read() as returning a char Wrong logic; it returns an int and -1 means end of file
Forgetting to close streams Resource leak; try-with-resources avoids this
Using byte streams carelessly for non-ASCII text Garbled characters

4. Serialization

4.1 The Problem and the Idea

A student management application holds Student objects in memory. When the program ends, they vanish. We want to save a Student to a file, close the application, and restore it later. A network application may also need to send objects to another program.

Serialization is the process of converting an object's state into a byte stream so that it can be stored or transmitted. The reverse process is deserialization. Serialization lets an object's state be preserved beyond the lifetime of a running program.

Analogy: vacuum-packing a record. You can store the pack in a drawer or post it to another office (serialization), then open it to get the same record back (deserialization). The analogy stops at one point: the restored object is a new object in memory with equivalent state, not the original one.

Why do we need serialization?

  • Saving object state to disk.
  • Transferring object data between Java applications.
  • Preserving application state.
  • Supporting legacy Java remoting (such as RMI) and object-storage mechanisms.
  • Demonstrating persistence of Java objects.

For modern web APIs, JSON or other explicitly defined data formats are often preferable to native Java serialization, especially when interacting with systems written in other languages.

4.2 The Serializable Interface

Java provides the Serializable marker interface (import java.io.Serializable;). It defines no methods; it marks objects of the class as eligible for Java's built-in serialization mechanism.

class Student implements Serializable {
    int rollNo;
    String name;
}

The main classes are:

  • ObjectOutputStream — writes objects (writeObject()).
  • ObjectInputStream — reads objects (readObject()).

implements versus extends: a class extends one superclass, but it can implements one or more interfaces, here Serializable, separated by commas when there are several (e.g., implements Serializable, Cloneable).

4.3 Serializing a Student Object

Goal: save Student(101, "Rahul", 92.5) to the file student.ser.

import java.io.*;

class Student implements Serializable {
    private static final long serialVersionUID = 1L;
    int rollNo;
    String name;
    double marks;

    Student(int rollNo, String name, double marks) {
        this.rollNo = rollNo;
        this.name = name;
        this.marks = marks;
    }
}

public class SerializationDemo {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul", 92.5);

        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream("student.ser"))) {
            oos.writeObject(s1);
            System.out.println("Object serialized successfully");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

Output: Object serialized successfully. The object is now stored in student.ser in binary form.

Syntax breakdown

Construct Explanation
implements Serializable Permission for Java to serialize this class
serialVersionUID A version identifier for the class (private static final long); recommended
new FileOutputStream("student.ser") Lower layer: writes bytes to the file
new ObjectOutputStream(...) Upper layer: converts objects into the serialized byte format
oos.writeObject(s1) Serializes s1 and sends the bytes down the chain
.ser extension A naming convention only; Java does not require it

Two layers cooperate: FileOutputStream handles the file's byte output, while ObjectOutputStream handles serialization (object to bytes). Think of the file stream as the delivery truck and the object stream as the packing machine in front of it.

4.4 Deserializing the Object

Deserialization reads a serialized object from a file (a sequence of bytes) and reconstructs it as an object in memory.

import java.io.*;

// Student class: same fields and serialVersionUID as in Section 4.3
// (constructor omitted here; it is not needed for reading).

public class DeserializationDemo {
    public static void main(String[] args) {
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream("student.ser"))) {

            Student s = (Student) ois.readObject();

            System.out.println("Roll No: " + s.rollNo);
            System.out.println("Name: " + s.name);
            System.out.println("Marks: " + s.marks);
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

Output

Roll No: 101
Name: Rahul
Marks: 92.5

Key steps

  1. Open the serialized file (student.ser) using FileInputStream.
  2. Wrap it with ObjectInputStream.
  3. Read the object with readObject() and type-cast it to Student.
  4. Access and print the object's fields.
Construct Explanation
(Student) ois.readObject() readObject() returns Object, so we cast it back to Student
catch (IOException | ClassNotFoundException e) Multi-catch: one handler for two unrelated exception types. readObject() may throw ClassNotFoundException if the class definition cannot be found

Note for Review (supplementary): For deserialization to work, the program must have access to the same Student class, and the serialVersionUID must match the one used when the object was saved. If the class changed incompatibly, Java rejects the old data. static fields are not part of an object's saved state, and fields marked transient are skipped.

4.5 How I/O and Serialization Work Together

Object serialization is built on top of Java's I/O stream system. ObjectOutputStream turns objects into a serialized byte representation and sends those bytes to an underlying stream; ObjectInputStream reads the bytes and reconstructs objects. Streams provide the transport (file, network, etc.); serialization handles the object conversion.

Direction Code Layers
Writing an object new ObjectOutputStream(new FileOutputStream("data.ser")) FileOutputStream writes bytes; ObjectOutputStream serializes
Reading an object new ObjectInputStream(new FileInputStream("data.ser")) FileInputStream reads bytes; ObjectInputStream deserializes
Feature I/O (Input/Output) Serialization
Purpose Transfer data Represent and restore object state
Data Bytes, characters, primitives, objects Java object graphs (objects and their references)
Main classes Stream, reader, writer classes (e.g., FileInputStream, BufferedReader) Object streams (ObjectOutputStream, ObjectInputStream)
Need Serializable? No Normally yes, for serializable classes
Example Read student names from a file Save and restore Student objects

Note for Review: Serialization uses I/O, but not every I/O operation involves serialization. Serialization sits around I/O: it is the object-conversion layer on top of the data-transfer layer.

4.6 Practical Example: Student Record Persistence

Using the Student class from Section 4.3 (with rollNo, name, marks):

// Serialize: save Student object to disk
Student s1 = new Student(101, "Rahul", 92.5);

try (ObjectOutputStream oos = new ObjectOutputStream(
        new FileOutputStream("student.ser"))) {
    oos.writeObject(s1);
    System.out.println("Student saved to disk.");
}
// Deserialize: read and reconstruct the Student object
try (ObjectInputStream ois = new ObjectInputStream(
        new FileInputStream("student.ser"))) {
    Student s2 = (Student) ois.readObject();
    System.out.println("Recovered Student:");
    System.out.println(s2.rollNo + " " + s2.name + " " + s2.marks);
}

Output

Student saved to disk.
Recovered Student:
101 Rahul 92.5

(The fragments assume the surrounding try/catch for IOException and ClassNotFoundException as in Sections 4.3 and 4.4.) Applications: student information systems, university management portals, and persisting records across sessions.

4.7 Complete Student Management Example

Goal: create a Student, serialize it to students.ser, deserialize it, and display the restored details.

import java.io.*;

class Student implements Serializable {
    private static final long serialVersionUID = 1L;
    int rollNo;
    String name;
    String department;

    Student(int rollNo, String name, String department) {
        this.rollNo = rollNo;
        this.name = name;
        this.department = department;
    }

    void display() {
        System.out.println("Roll No: " + rollNo);
        System.out.println("Name: " + name);
        System.out.println("Department: " + department);
    }
}

public class StudentManagement {
    public static void main(String[] args) {
        Student s1 = new Student(101, "Rahul", "CSE");

        // Serialize: save the student object
        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream("students.ser"))) {
            oos.writeObject(s1);
            System.out.println("Student saved.");
        } catch (IOException e) {
            e.printStackTrace();
            return;
        }

        // Deserialize: read the student object
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream("students.ser"))) {
            Student s2 = (Student) ois.readObject();
            System.out.println("Student restored:");
            s2.display();
        } catch (IOException | ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}

Output

Student saved.
Student restored:
Roll No: 101
Name: Rahul
Department: CSE
Step Operation Result
1 Define Student implements Serializable Class becomes eligible for serialization
2 Create s1 Object in memory (101, Rahul, CSE)
3 oos.writeObject(s1) Bytes written to students.ser; message printed
4 ois.readObject() and cast New Student object s2 rebuilt from the bytes
5 s2.display() Restored details printed

The return; in the first catch stops the program if saving fails, since there would be nothing to restore.

4.8 Common Serialization Mistakes

Mistake Consequence
Treating Serializable as if it had methods to implement It is a marker interface; nothing to implement
Forgetting the (Student) cast on readObject() Compile-time type error (Object is not Student)
Not catching ClassNotFoundException when reading Compile-time error (checked exception)
Expecting s2 == s1 after restoring Restored object is a different object with equal state

5. Packages

5.1 The Problem and the Idea

A university application will have a Student class, a Faculty class, a Course class and many more. Large projects can easily contain two different classes with the same name (for example, a Student for exams and a Student for a library), and thousands of files are hard to navigate.

A package is a namespace used to group related Java classes, interfaces, enums, records, and other types. Packages are useful for organizing code, avoiding naming conflicts, and controlling access between classes.

Analogy: folders on a computer. Two files named report.txt can coexist if they sit in different folders. The analogy fits because a package name also maps to a directory structure.

Why use packages?

  • Organize code into meaningful modules.
  • Avoid naming conflicts (e.g., Student in different packages).
  • Control access between classes (using access modifiers).
  • Improve maintainability and reusability.

Directories typically map to package names: the package university.students lives in the folder university/students/.

5.2 Defining and Using a Package

General pattern

package packageName;      // first statement in the file

import other.package.ClassName;   // optional, after the package line

public class MyClass { ... }
// File: Student.java
package university.students;

public class Student {
    private int rollNo;
    private String name;
    // ...
}
// File: UniversityApp.java
import university.students.Student;

public class UniversityApp {
    public static void main(String[] args) {
        Student s = new Student();
        // ...
    }
}
Construct Explanation
package university.students; Declares which package this file's class belongs to; must be the first statement (comments aside); at most one per file
Dot in the name Separates package levels: students is a sub-package of university
import university.students.Student; Lets us write Student instead of the full name
public class Student public is required for a class to be used from another package

Key takeaways: a package groups related types, provides a unique namespace, helps in large modular applications (e.g., a university system), and directories typically map to package names.

5.3 Types of Packages

Java packages fall into two types:

  • Built-in packages: provided by the Java platform (e.g., java.lang, java.util).
  • User-defined packages: created by programmers to organize application code (e.g., university.students).
Package Purpose Common classes (examples)
java.lang Core language support String, Math, Object
java.util Utilities and collections Scanner, ArrayList, HashMap
java.io Traditional I/O File, FileInputStream, Serializable
java.nio.file Modern file operations (NIO.2) Path, Files
java.net Networking Socket, URL
java.time Date and time APIs LocalDate, LocalDateTime
java.sql Database connectivity (JDBC) Connection, ResultSet

Note for Review: Classes in java.lang are available without an explicit import. This is why String, Math, Object and Cloneable work without any import line.

5.4 Creating a User-Defined Package

Project structure (source files)

(Parent Directory)
├── mypackage/
│   └── Student.java
└── Main.java
// File: mypackage/Student.java
package mypackage;

public class Student {
    public void display() {
        System.out.println("Hello from the Student package");
    }
}
// File: Main.java
import mypackage.Student;

public class Main {
    public static void main(String[] args) {
        Student s = new Student();
        s.display();
    }
}

Compile and run

> javac -d . mypackage/Student.java Main.java
> java Main

Output: Hello from the Student package

Item Explanation
package mypackage; Declares the package of the class
import mypackage.Student; Makes Student usable by its simple name
public (class and method) Allows access from another package
javac -d . Directs the compiler to place .class files into directories matching the package names

After compilation, mypackage/Student.class and Main.class exist in the parent directory; the class files are laid out to match the package name.

5.5 Importing Packages

Java supports different import patterns:

# Pattern Effect
1 import java.util.Scanner; Imports only Scanner from java.util
2 import java.util.*; Imports all accessible (public) types from java.util, but not sub-packages
3 java.util.Scanner sc = new java.util.Scanner(System.in); Fully qualified name; no import needed

So import java.util.*; gives Scanner, ArrayList and HashMap, but not java.util.regex.Pattern, because regex is a sub-package.

5.6 Access Modifiers and Packages

Access modifiers determine visibility:

Modifier Same class Same package Subclass in another package Unrelated class in another package
public Yes Yes Yes Yes
protected Yes Yes Yes, with restrictions No
No modifier (package-private) Yes Yes No No
private Yes No No No

For protected, cross-package access through inheritance follows Java's specific qualifying-reference rules; it is not equivalent to unrestricted public access.

Program 14: access between packages

// File: college/Student.java
package college;

public class Student {
    public String name = "Rahul";
    private int password = 1234;

    public void display() {
        System.out.println(name);
    }
}
// File: Main.java
import college.Student;

public class Main {
    public static void main(String[] args) {
        Student s = new Student();
        System.out.println(s.name);
        s.display();
        // System.out.println(s.password);
        // Error: password has private access
    }
}

Output

Rahul
Rahul

s.name works because name is public. s.display() works because the method is public, and inside Student the method may use anything in its own class. s.password is rejected at compile time: the private field is accessible only inside Student, even if the accessing class were in the same package.

5.7 Static Imports

Static imports allow static members to be referenced without writing the declaring class name.

import static java.lang.Math.PI;
import static java.lang.Math.sqrt;

public class StaticImportDemo {
    public static void main(String[] args) {
        double radius = 5.0;
        double area = PI * radius * radius;
        System.out.println("Area = " + area);
        System.out.println("Square root = " + sqrt(25));
    }
}

Output

Area = 78.53981633974483
Square root = 5.0

The area uses the formula A=πr2 with r=5.0, so A=π×25≈78.54. Both area and radius are double because the values are decimal. sqrt(25) returns a double, which prints as 5.0. Without static imports, we would write Math.PI and Math.sqrt(25).

5.8 Common Package Mistakes

Mistake Consequence
Folder structure not matching the package name Compiler/JVM cannot find the class
Forgetting public on a class used from another package Compile-time error: class is not public in its package
Assuming import x.*; includes sub-packages Classes from sub-packages remain unresolved
Confusing import with import static import brings in types; import static brings in static members

6. Integrated Example

We now combine all four ideas into a small university application: the Student model is cloneable and serializable, a separate storage class performs I/O with object streams, and packages keep the model and storage logic apart.

Project structure

UniversityApplication/
├── university/
│   ├── model/
│   │   └── Student.java
│   └── storage/
│       └── StudentStorage.java
└── Main.java

Who does what?

  • Student (package university.model) holds the data and supports cloning and serialization.
  • StudentStorage (package university.storage) saves and loads students with ObjectOutputStream and ObjectInputStream (I/O).
  • Main creates, clones, saves and restores.

Dependencies: StudentStorage uses Student; Main uses both.

6.1 university/model/Student.java

package university.model;

import java.io.Serializable;

public class Student implements Serializable, Cloneable {
    private static final long serialVersionUID = 1L;
    private int rollNo;
    private String name;
    private String department;

    public Student(int rollNo, String name, String department) {
        this.rollNo = rollNo;
        this.name = name;
        this.department = department;
    }

    @Override
    public Student clone() {
        try {
            return (Student) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    public void setName(String name) { this.name = name; }

    public void display() {
        System.out.println(rollNo + " " + name + " " + department);
    }
}

The three instance fields are primitives or immutable Strings, so a shallow clone is sufficient to give the two Student objects independent state. This clone() catches CloneNotSupportedException itself (it cannot happen because the class implements Cloneable), so callers need no throws. AssertionError signals "this should be impossible".

6.2 university/storage/StudentStorage.java

package university.storage;

import university.model.Student;
import java.io.*;

public class StudentStorage {

    public static void save(Student s, String file)
            throws IOException {
        try (ObjectOutputStream oos = new ObjectOutputStream(
                new FileOutputStream(file))) {
            oos.writeObject(s);
        }
    }

    public static Student load(String file)
            throws IOException, ClassNotFoundException {
        try (ObjectInputStream ois = new ObjectInputStream(
                new FileInputStream(file))) {
            return (Student) ois.readObject();
        }
    }
}

save and load are static, so we call them with the class name (StudentStorage.save(...)) without creating a StudentStorage object. Both methods declare throws and let the caller decide how to handle failure.

6.3 Main.java

import university.model.Student;
import university.storage.StudentStorage;

public class Main {
    public static void main(String[] args) throws Exception {
        Student original = new Student(101, "Rahul", "CSE");
        Student cloned = original.clone();
        cloned.setName("Amit");

        System.out.println("Original:");
        original.display();
        System.out.println("Cloned:");
        cloned.display();

        StudentStorage.save(cloned, "studentdata.ser");
        Student restored = StudentStorage.load("studentdata.ser");
        System.out.println("Restored:");
        restored.display();
    }
}

Compile and run

> javac -d . university/model/Student.java university/storage/StudentStorage.java Main.java
> java Main

Output

Original:
101 Rahul CSE
Cloned:
101 Amit CSE
Restored:
101 Amit CSE

Execution trace

Step Operation Result
1 new Student(101, "Rahul", "CSE") original created
2 original.clone() New Student with identical fields; cloned refers to it
3 cloned.setName("Amit") Only the clone's name changes (String is replaced, not shared state)
4 Print both 101 Rahul CSE and 101 Amit CSE
5 StudentStorage.save(cloned, ...) Clone's state serialized to studentdata.ser
6 StudentStorage.load(...) New Student rebuilt from the file
7 restored.display() 101 Amit CSE, because we saved the clone

Process flow: Student object → clone → serialize (save to file) → deserialize (load from file) → retrieved object.

Note for Review: Class files are produced under university/model/ and university/storage/ because of javac -d .. The cross-package calls work because Student and its used methods are public.

6.4 A Second Version, and a Pitfall to Notice

A compact variant of the same project uses a Student with fields id, name and cgpa (all private), a toString() method for printing, and StudentStorage as above:

Student s1 = new Student(101, "Ananya", 9.1);
Student s2 = s1.clone();                              // Cloning
s2 = new Student(102, "Ananya (Cloned)", 9.1);        // see note below
StudentStorage.save(s2, "student.ser");               // Serialization
Student s3 = StudentStorage.load("student.ser");      // Deserialization
Original     : Student[id=101, name=Ananya, cgpa=9.1]
Cloned       : Student[id=102, name=Ananya (Cloned), cgpa=9.1]
Deserialized : Student[id=102, name=Ananya (Cloned), cgpa=9.1]

Pitfall (clarification of the slide): In this variant the line s2 = new Student(...) replaces the reference returned by s1.clone(), so the cloned object is discarded and the clone call has no effect on the final output. The output is produced by the new object. Because id, name and cgpa are private with no setters, the author builds a fresh object to get different data. To keep the genuine clone and modify it, add a setter (as setName does in Section 6.1) and change the clone instead of reassigning s2.
