Introduction to Backend Systems

Picture a restaurant. The dining room is what the customer sees and touches. The kitchen is where orders are interpreted, ingredients are fetched and quality is enforced. A web application is split the same way. In the client-server paradigm discussed earlier, the client side is the browser, the front end, where the user interacts with the system. Everything else lives at the back end.

  • The backend is everything that runs on the server rather than in the user's browser.
  • It may not be a single server. As the application scales up, many threads of operations have to run, and depending on how the back-end architecture is organized there may be a couple of servers or hundreds of them.
  • Application logic: the rules that decide what a request should actually do. The request is the HTTP request coming from the client; on receiving it, the application logic residing on the server decides what is to be done.
  • Data access: reading from and writing to a database, safely and consistently. The data store can be treated as one abstraction even though it may physically consist of many servers, and the database system is the software that manages the data in it. A request may be a read, or an update; the database is accessed accordingly, and the information fetched travels back as a response that is rendered in the client's browser.
  • A backend can be written in many languages (PHP, Java and others), but its job is always the same: decide what happens, and keep the data correct.

Where MVC Fits

Recall from Module 4 the Model-View-Controller (MVC) split. The frontend is roughly the View; the backend usually houses the Model and the Controller.

MVC part Lives at Job
View Front end (browser) Shows the rendered information; where the user interacts
Model Back end The data and the rules for keeping it correct
Controller Back end Decides what a request should do

Note for Review: The shorthand to remember is M(V)C: only the V is at the front end; MC → Backend.

What Is a Web Server

A web server is the program that listens for HTTP requests and sends back responses. It is a piece of code with a listening port: one process thread (a thread being a single flow of control) is dedicated to listening on that port and waiting for requests.

The listener is the heart of a web server: a dedicated thread that sits on a port and does nothing but wait for HTTP requests. Requests from many clients, for example the users of a busy booking site such as IRCTC, pile up in a request queue and are served first come first serve, or by some other priority rule. One thread cannot do everything, so the server is designed as a multithreaded process. One thread may contact the database system to fetch or update data in the data store, another may run microservices by calling their dedicated APIs, and all of this happens in parallel before the responses are sent back.

What the server does with a request depends on what was asked for.

  • Static files: for a plain HTML (the placeholder or markup), CSS, JS or image file, the server just reads it off the disk. It searches for the file wherever it is stored and returns it unchanged. Nothing is modified; the content is well defined and does not change.
  • Dynamic requests: the server instead hands the request off to an application, which builds the response on the fly, adding something based on the request and the current context. The result is not sitting in storage waiting to be sent.
  • Common web servers: Apache (very widely used), Nginx and Microsoft IIS. Node.js can act as its own lightweight server.
  • In practice, one machine often plays both roles: serving static assets directly, and forwarding everything else to the backend application.

Note for Review: Keep the two ideas apart. The web server (Apache, Nginx, IIS) is the program that listens and answers; the application (PHP code, a Node.js program) is what builds a dynamic answer. One machine commonly runs both.

Static vs Dynamic Content Revisited

The task set of the web server changes with the kind of content.

Static site Dynamic site
Content for a URL The exact same hard-coded content, every single time Built at least partly fresh for each request
Where it comes from A stored file Usually data pulled from a database into an HTML template
What changes Nothing on demand The data; the database always holds the current state, while the HTML markup stays the template and remains the same

Why it matters at scale. Think of Amazon, Flipkart or any online shopping portal. The scale has a major impact on how the back end is designed. A retailer cannot hand-write a page for every product, and cannot edit each page by hand every time something changes. A template plus a database scales to millions, even billions, of pages.

Static resources (CSS, JS, images) are still served as plain files, even on an otherwise fully dynamic site. Keeping the two kinds separate is what lets each be handled in the most optimal way as the site scales.

Server-Side Processing

Whatever the user's action, the backend maps it onto the matching SQL operation before it ever touches the database.

The server-side code is where all of this is orchestrated:

  1. Decode. The HTTP request arrives from the browser and the application logic decodes it to find out which task is to be performed.
  2. Act. Depending on the request, the backend can enter new data, read existing data, update it or delete it. These are the CRUD operations (Create, Read, Update, Delete) discussed earlier, each mapped to the matching SQL operation.
  3. Receive. The database returns rows, a result set.
  4. Encode. The server-side code embeds the result into the dynamic part of the page and encodes the response as either HTML or JSON, and sends it back to the browser. With JSON, the client side then executes something to turn the data into what the user sees.

This decode, act, receive, encode cycle is what the web server's server-side code typically performs.

Why Server-Side Code

  • Efficient storage and delivery: one database and one template can generate millions of pages instead of hand-writing each one. Once the logic for what to do is coded, it runs automatically; nobody checks every page and repeats the work manually.
  • Customized experience: saved preferences, order history and recommendations are all server-side lookups. The response can be tailored to a specific user's profile and session.
  • Controlled access: a bank shows each customer only their own accounts, decided entirely on the server. Whenever a request arrives, the server must verify whether the sender is allowed to make it, so only authorized clients get through. Any financial transaction or other sensitive request therefore needs an entry point where this check is done, and that entry point is on the server.
  • Sessions and notifications: remembering who is signed in, and sending confirmation emails or alerts. HTTP is a stateless protocol, so remembering who signed in, building up a profile, saving preferences and keeping a history of past behaviour all have to be enforced at the server. That history can feed targeted advertising, but it also enables a genuinely customized experience.
  • Amazon's recommendations, a bank's account page and a social feed are all, underneath, server-side programming.

Introducing PHP

PHP ("PHP: Hypertext Preprocessor", a recursive acronym) is a scripting language designed from the start to run on a web server.

  • Embedded in HTML: just as CSS and JavaScript can be embedded in a page, PHP code sits inside <?php ... ?> tags in an otherwise ordinary .php file. Everything outside those tags is sent as plain HTML. The tags tell the server that what lies between them is PHP to be interpreted, not markup; alternatively the whole file can be pure PHP saved with the .php extension.
  • Runs before the response leaves the server: the browser only ever receives the finished HTML, never the PHP source.
  • Talks to databases directly: extensions such as PDO (PHP Data Objects) connect to MySQL, PostgreSQL and others with the same API. The database is a separate entity of your choice; the API (application programming interface) is the anchor point through which the PHP program calls the database's functionality.
  • Powers a very large share of the web, including WordPress, typically as the "P" in the classic LAMP stack: Linux, Apache, MySQL, PHP.

PHP in Action

Listing the instructors of the Computer Science department of the university database:

Everything between <?php and ?> runs on the server. The script first creates a PDO object, an instance just like creating an object in C++ or Java, which carries the address of the database (localhost), its name (university) and the credentials that grant access. It then runs a SQL query, the same select statement seen in the SQL lectures that asks for the name and salary of every instructor in the Computer Science department, and keeps the outcome in the variable $stmt. Since the outcome has many rows, a foreach loop visits each instructor and echoes one line of HTML. Adding the dollar sign and the <br> tag here is the view part: the database itself stores only the plain number. 

<?php
$pdo = new PDO(
  'mysql:host=localhost;dbname=university', 'user', 'pass'
);
$stmt = $pdo->query(
  "select name, salary from instructor
   where dept_name = 'Comp. Sci.'"
);
foreach ($stmt as $row) {
  echo $row['name'] . ' - $' . $row['salary'] . '<br>';
}
?>

list_instructors.php, rendered in the browser (HTML sent to browser):

output (HTML sent to browser)
Srinivasan - $65000
Katz - $75000
Brandt - $92000

The result is the same Comp. Sci. query and result as the SELECT command in SQL. PHP just runs it on the server and writes plain HTML in its place before the page is sent.

Reading the Code Piece by Piece

Piece of code What it does
new PDO(...) Creates the connection object (an instance of the PDO type)
'mysql:host=localhost;dbname=university' Names the driver, the server and the database
'user', 'pass' The credentials that decide who may access the database (access control)
$pdo->query("select ...") Sends the SQL query to the database; the outcome is stored in $stmt
foreach ($stmt as $row) A loop over the result: one pass per row, that is, per instructor

Note for Review: The query here is a plain string built by the programmer. PDO can also prepare a statement with placeholders, which is the safer habit whenever user input enters a query (compare the ? in the Node.js example next).

Introducing Node.js

Node.js is a JavaScript runtime that runs outside the browser. At the server side, if you want to use JavaScript, you popularly use Node.js. The same language now powers both frontend and backend, which gives more flexibility.

  • Built on Chrome's V8 engine: designed around non-blocking, event-driven I/O, which makes it well suited to handling many connections at once. If you are looking for scalability, with many requests to serve, this is an efficient way to handle them because work proceeds in parallel instead of waiting.
  • npm: Node's package manager gives access to a huge ecosystem of reusable packages, including database drivers. You do not start from scratch; the functions already exist and you call them.
  • Usually paired with a framework: Express.js handles routing, while a driver or ORM (e.g. mysql2, pg, Sequelize) handles the database. The framework makes the whole setup more powerful.
  • Recall from Module 4: Node.js is what let JavaScript move off the browser and onto the server in the first place.

Note for Review: Of the three names in the brackets, mysql2 and pg are drivers (they talk to MySQL and PostgreSQL), while Sequelize is an ORM (it maps database rows to JavaScript objects).

Node.js in Action

The same instructor listing, now in JavaScript:

Node.js has no page to embed code into, so the script is an ordinary program. It loads the mysql2/promise driver with require, then defines an async function so the slow database calls can be awaited without freezing everything else. createConnection opens the link to the university database on the same machine, and execute runs the query directly: the SQL goes in as an argument, with a ? placeholder that receives 'Comp. Sci.', instead of first being saved in a variable. The result rows is an array of rows, forEach walks through it, and console.log prints each line. In the template literal, ${...} evaluates an expression and places its value, while the $ just before it is the literal currency symbol. 

const mysql = require('mysql2/promise');

async function listCompSciInstructors() {
  const conn = await mysql.createConnection({
    host: 'localhost', database: 'university'
  });
  const [rows] = await conn.execute(
    'select name, salary from instructor where dept_name = ?',
    ['Comp. Sci.']
  );
  rows.forEach(r => console.log(`${r.name} - $${r.salary}`));
}

listCompSciInstructors();

list_instructors.js, console output (server console):

output (server console)
Srinivasan - $65000
Katz - $75000
Brandt - $92000

Same query, same result as the PHP example, but Node.js does not embed in a page. It runs as its own long-lived server process (commonly via Express) that stays up and handles every incoming request.

Reading the Code Piece by Piece

Piece of code What it does
require('mysql2/promise') Loads the pre-existing database driver package
async function ... A function whose slow steps can be awaited
mysql.createConnection({...}) Function call that establishes the connection to the university database on localhost
conn.execute(sql, [values]) Runs the query on the connection object conn, which is the handle to the connected database; each ? is filled from the array
rows The set of all returned rows (tuples)

console.log(...) The print function; here it writes to the server console, not to a web page

PHP and Node.js Side by Side

HTTP Is Stateless

Imagine a festival where the gate staff forget your face the instant you walk past. Every time you return, you start from zero. That is HTTP by default.

  • By default, HTTP treats every request as brand new; the server has no memory of any earlier request from the same browser.
  • Earlier, this statelessness was presented as an advantage, and it is deliberately kept. But it becomes a problem the moment an app needs to remember anything: that you are logged in, what is in your cart, your language preference, or your browsing history.
  • The fix is not a change to HTTP itself. It is a small piece of data the browser carries along and hands back on every request.
  • That small piece of data is a cookie.

Cookies have a downside, seen earlier: they can be used for targeted advertisements and for building a pattern of a client's behaviour as they browse different websites. But they are also what gives the web a memory.

Cookies

The first box is what the server sends: a normal 200 OK response (status 200 means the fetch succeeded) with one extra header, Set-Cookie, which hands the browser a session_id. The browser stores it, and on the next request to the same site, here GET /dashboard, it automatically adds a Cookie header carrying the same value. That repeated value is how the server stitches separate, otherwise unrelated requests together as coming from one browser. This is why a shopping cart can still hold the items you put in earlier but never bought.

server-response.http

HTTP/1.1 200 OK
Content-Type: text/html
Set-Cookie:
  session_id=a3fWa9k2

next-browser-request.http

GET /dashboard HTTP/1.1
Cookie:
  session_id=a3fWa9k2

A cookie is a small piece of data the server asks the browser to store and send back with every later request to that same site.

Note for Review: A cookie is only a carrier. It usually holds just an identifier; the real information (who you are, what is in the cart) is looked up on the server. Also, a cart surviving after you close the browser needs either a cookie that outlives the browser session (see Expires / Max-Age below) or the cart being stored on the server against your account.

How a Session Works

A sign-in walkthrough, step by step:

A login is a conversation of five short turns. First, the browser sends the credentials with a POST request; POST rather than GET because the password then travels in the body of the message instead of in the URL. Second, the server checks the credentials, which is the authentication step, and if they are fine it answers OK together with a Set-Cookie header carrying a fresh session id. Third, the browser stores that cookie. Fourth, every later request carries it back automatically. Fifth, the server finds the session still valid and returns a personalized page.

Cookies are what let an inherently stateless protocol like HTTP remember who you are between requests.

Cookie Attributes You Should Know

Attribute What it does
Expires / Max-Age Turns a session cookie (gone when the browser closes) into a permanent one that survives until a set date. It defines how long the cookie is treated as valid
HttpOnly Blocks JavaScript from reading the cookie at all, an important defense against script-based attacks
Secure The cookie is only ever sent over HTTPS, never plain HTTP, which adds another layer of defense
SameSite Controls whether the cookie is sent on cross-site requests or only from the same site; Strict or Lax is the safe default for anything login-related

A login session cookie should almost always be HttpOnly, Secure, and SameSite=Lax or Strict. For example (the header is folded onto two lines only for readability):

Set-Cookie: session_id=a3fWa9k2;
            Max-Age=3600; HttpOnly; Secure; SameSite=Lax

Note for Review: Why HttpOnly matters: if an attacker manages to inject a script into a page, that script runs in the user's browser with access to the page's cookies. With HttpOnly set, the script cannot read the session cookie, so it cannot steal the login.

Authentication Basics

Authentication is the process of verifying that someone is who they claim to be. It is a responsibility of the server: it has to make sure there is no imposter pretending to be someone else. There are three families of evidence:

Factor Examples
Something you know A password or PIN
Something you have A phone, a hardware key, a one-time code
Something you are A fingerprint or face scan

Multi-factor authentication (MFA) combines two or more of these. A password plus a one-time code is the most common example, and MFA is very common nowadays. How authentication is carried out is a whole domain of its own; this is just the idea that the web server also carries this duty.

Authentication answers "who are you?"; authorization, a separate question, answers "what are you allowed to do?".

Password Storage and Hashing

The server stores passwords too, because that is how it verifies them at every login, but a password should never be stored as plain, readable text. If the database ever leaks, every account leaks with it.

  • Hashing: a one-way mathematical function turns a password into a fixed-length string that cannot practically be reversed. You cannot apply an inverse of the function to recover the original plain text; that is the essence of hashing.
  • Salting: a random value is mixed in per user, so two identical passwords do not produce identical hashes. If A and B both choose the same plain-text password, their stored hashes still differ.
  • At sign-in, the server hashes the entered password again and compares the two hashes. It never needs to know the original password.
  • This is why a legitimate site can only send you a password reset link, never your actual forgotten password.

In symbols, with H the hash function, the value kept in the database is

hstored​=H(salt∥password)

and a sign-in attempt succeeds exactly when

H(salt∥attempt)=hstored​

Going forwards is easy; going back is not, since there is no practical H−1 that recovers the password from hstored​.

The upper path of the figure is sign-up and the lower path is every later sign-in. At sign-up, the plain-text password, typed on the client and carried to the server in the HTTP request, goes through a one-way hash together with a random per-user salt, and only the result is kept in the database. At sign-in the server repeats exactly the same computation on what was typed and compares the two hashes. A match means authenticated, a mismatch means rejected. The original password is never needed, and never stored.

Note for Review: Hashing is not encryption. Encryption is designed to be reversed with a key; a hash is designed so it cannot be. The salt is not a secret: it is stored next to the hash, and its only job is to make identical passwords look different and to stop one precomputed table from cracking many accounts at once. In practice, deliberately slow password-hashing functions such as bcrypt or Argon2 are preferred over fast general-purpose hashes.

Logging Into a Website

A practical scenario that ties everything together: a student enters their ID and password on a course portal's login page and clicks submit.

  1. Submit: the browser sends both values to the server over HTTPS, as a request message.
  2. Verify: the server hashes the submitted password and compares it against the stored hash for that student ID.
  3. Start a session: on a match, the server creates a session record in a database and responds with Set-Cookie: session_id = .... Every session gets a unique id, just like a primary key for a record in a table, and that id is what is returned.
  4. Stay signed in: every later request automatically carries that cookie, so the server recognizes the student without asking again.
  5. Sign out: signing out deletes the session on the server (a database access that removes that record) and clears the cookie. The trust, not just the data, is what gets revoked.

Signing out and deleting your account are two different things. After signing out you can sign in again, because your account entry, with its hashed password, is still in the user database. Only the session id was deleted from the session database.

Backend Module Recap

  • Databases replaced ad hoc file storage to solve redundancy, integrity and concurrent-access problems in one place, giving concurrent access for CRUD operations and the other data-retrieval techniques of SQL.
  • The relational model organizes data into tables; SQL is the declarative language used to define (DDL) and query (DML) them, including in, between, like and subqueries.
  • CRUD: Create, Read, Update, Delete covers essentially everything an application does to its data: insert, select, update, delete.
  • A backend is server-side code plus a database. PHP embeds in HTML and Node.js runs as a standalone process, but both exist to run the same SQL against the same database. This is mostly the Model and Controller part of MVC.
  • Cookies give stateless HTTP a memory, sessions use that memory to track a signed-in user, and authentication verifies who that user is.

Roadmap of the Frontend Module

Open a social feed and scroll through posts, comments and likes. The page never flashes white and never freezes, even though data is arriving from a distant server. That is the key question of this module: why does this page never reload?

What the module covers:

  • Modern frontend development: what has changed since plain DOM manipulation.
  • Component-based interfaces, the idea around which React, Vue, Angular and Svelte revolve.
  • State and event handling as part of a component.
  • Frontend frameworks: a basic overview of React, Vue and Angular, with their pros and cons and trade-off analysis.
  • Single-page applications (SPA): a newer idea that changes the whole frontend job.
  • REST APIs and public APIs: how data is obtained from the back end, which you will use when building your own web application.

This lecture covers the first part of that list: the move from DOM manipulation to components, state, events and one-way data flow. Frameworks, SPAs and APIs come next. The reason all of this matters is cost: the choices made here decide the overhead, the time taken and, finally, the user experience.

Modern Frontend Development

At its core, frontend development is still exactly what Modules 1 to 3 covered: HTML, CSS and JavaScript running in the browser. HTML and CSS are the blueprint of the page; JavaScript makes it behave.

What has changed? The scale and interactivity expected of that JavaScript has grown enormously. Users scroll at speed on mobile phones, talk to speech-based interfaces, and like and comment constantly. The amount of information flowing and the expectation of responsiveness have both grown tremendously.

The DOM manipulation approach: the DOM is a hierarchical tree (HTML, head, body and the elements below them) that shows how document objects sit with respect to each other. To make a page interactive you:

  1. select an element,
  2. attach a listener to it (an event listener: what should happen when something occurs on that element, such as a click on a button, a checkbox tick or a form submit),
  3. manually update the page when the event fires.

This is workable for a few widgets. But today's applications (inboxes, dashboards, social feeds) have hundreds of small, moving, interdependent pieces of UI, which is a different ball game altogether. So "modern frontend development" mostly means the tools and patterns built to manage that complexity. The growth in UI complexity is what led the frontend area to be re-imagined.

From Static Pages to Rich Applications

The three eras differ in how much of the page is rebuilt per interaction. A static page is fetched once, and nothing changes without a full reload. In a dynamic page the server rebuilds the HTML fresh for each request, so a click still often means a full reload. Every click, every scroll and every other trigger would cost one, which becomes seriously expensive as interfaces grow more complex. In a rich frontend application the page is loaded once; afterwards JavaScript owns it, asks the server only for data and updates just the affected pieces in place.

Each stage still relies on the layer below it. A rich frontend app still sends HTTP requests and still renders HTML; far more of it simply happens client-side.

Note for Review: The answer to "why does the page never reload?" is the third row: after the first load, the browser asks only for data (small JSON, or a small HTML piece) and JavaScript patches the page in place. HTTP and HTML have not gone away.

Component-Based UI

A component is a self-contained, reusable piece of UI that owns its own markup, data and behaviour together. Reusability is what gives it the fundamental push towards making small updates possible.

  • Before components: a page's markup, styling and JavaScript logic for one widget were often scattered across a whole file (or several), so wherever the widget appeared, every change had to be made in several places.
  • With components: a TaskItem or LikeButton is one unit you can build, test and reuse anywhere.
  • This is the organizing idea behind essentially every major frontend framework in use today.

This does not overturn MVC, which still has its purpose. It only concerns how the front end reflects change without repeated reloads as complexity grows.

Before components, one widget, say a Like button, was smeared across three files: markup in index.html (1), styling in styles.css (2) and click behaviour in app.js (3). To change the button you had to hunt through all three. The same widget reappears in the news feed, on photo posts and in comment threads, so every change multiplied. The result was a codebase where you scroll, search and hope nothing else breaks.

index.html (1)

<!-- markup for the Like button lives here -->
<div class="like-btn" onclick="...">

styles.css (2)

/* styling for the Like button lives here */
.like-btn { color: #333; ... }

app.js (3)

// click behaviour lives here
function handleLike() { ... }

Same widget. Three files. Scroll, search, and hope nothing else breaks.

With a component, the same Like button is a single LikeButton.jsx file (JSX stands for JavaScript XML, markup written inside JavaScript). Inside it, the markup, the state (the count) and the logic that increments it sit together. That one component is placed in the news feed, in a photo post and in a comment thread, and each instance keeps its own state, so the counts can be 128, 54 and 9. It is reused, not rewritten: the same component on every screen.

Before: hunt through 3 files to change one button. After: edit LikeButton.jsx once, and every screen using it updates.

Anatomy of a Component

A TaskItem component shows the three parts every component has. The template (markup) is what the user sees: a label, a checkbox and a delete button. The state (data) is this task's own text and its done / not-done flag. The logic (behaviour) is what happens on a click: toggle done, or fire delete. A component bundles all three together, so changing the state re-renders the template automatically, and nobody has to hop between an HTML, a CSS and a JavaScript file as before.

Part Holds In TaskItem
Template (markup) What the user sees A label, a checkbox, a delete button
State (data) What the component remembers The task's own text and a done / not-done flag
Logic (behaviour) What happens when the user acts Toggle done, fire delete

A Button Component Two Ways

The same Like button written in the earlier style and in React. Same behaviour, two philosophies.

In the earlier, vanilla JavaScript style, the button is plain HTML and everything else is done by hand. A count variable lives in the script, outside the markup. getElementById finds the element, addEventListener attaches the click behaviour separately, and inside the handler you increment the count and then manually overwrite the button's text. If you forget that last step, the number changes in memory but not on the screen.

vanilla-js (earlier style)

<button id="likeBtn">Like (0)</button>
<script>
  let count = 0;
  const btn = document.getElementById('likeBtn');
  btn.addEventListener('click', () => {
    count++;
    btn.textContent = `Like (${count})`;
  });
</script>

The React version is a function that returns the markup. The state is declared with useState(0), which gives back the current count and a setter setCount. The handler is written directly on the button as onClick, and all it does is change the state. React notices and re-renders the button with the new number. Nothing is looked up by id and nothing is patched by hand, and the same function can be reused for any number of buttons.

LikeButton.jsx (React)

function LikeButton() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Like ({count})
    </button>
  );
}

Vanilla JS manually finds and mutates the element; React re-renders the button from its own state whenever count changes.

What happens on a click Vanilla JS React
Finding the element getElementById('likeBtn') No lookup; the handler sits on the element itself
Updating the number count++ setCount(count + 1)
Updating the screen Your code: btn.textContent = ... React re-renders from the new state

Composing Components

Components nest. A whole UI is a tree of them.

Each box is its own reusable component; a TodoList doesn't know or care how many TodoItems it holds. Control is confined: the list simply hands each task to an item component, and every item keeps its own scope, so each to-do is different even though the component is the same.

State and the Data Behind the UI

State is the data a component holds onto between renders. It is what the UI is currently showing. Between one render and the next the state stays as it is; whenever it changes, another render happens.

  • Not the same as database state: component state usually lives only in the browser, for as long as the page is open. Clicking Like and seeing a counter go from 56 to 57 does not by itself change anything at the server.
  • When state changes, the framework re-renders whatever part of the UI depends on it, automatically.
Kind of state Meaning Example
Local state One component's own data Whether one task is checked off
Shared / lifted state Data that several components need, usually held by their common parent instead The task list that both the items and a footer count depend on

Note for Review: Do not mix up component state (in the browser, gone when the page closes) with database state (at the back end, persistent). Exams like asking which one survives a page refresh.

A Counter Component with State

useState is imported from React. Inside Counter, the call useState(0) returns a pair: the current value (count) and a setter (setCount), and the 0 is the initial value. The returned markup shows the count and has two buttons whose onClick handlers call the setter with count + 1 and count - 1. Calling a setter is the signal that makes React re-render this component, so the new number appears without any manual DOM update.

Counter.jsx

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(count - 1)}>-1</button>
    </div>
  );
}

useState(0) gives back the current value and a setter; calling the setter is what tells React to re-render this component.

Trace of one click on +1 when count is 0:

  1. The onClick handler runs setCount(0 + 1).
  2. React records the new state, 1, and re-renders Counter.
  3. The function runs again, this time with count equal to 1, and the paragraph now shows Count: 1.

Note for Review: Never change count directly (for example count++). The variable would change but React would not be told, so nothing re-renders. Always go through the setter.

Event Handling in Modern Frontends

Recall from DOM manipulation: an event is anything that happens in the browser: a click, a keypress, a page load.

Imperative style (vanilla JS) Declarative style (frameworks)
How the handler is wired Select the element, then separately attach a listener to it Write the handler directly where the element is defined, e.g. onClick={...}
Where the handler lives Away from the markup it belongs to Right inside the markup it belongs to

The event itself has not changed. What has changed is how directly the handler is tied to the markup it belongs to. That small shift is a game changer for how the work is done, and it makes event handling far more scalable.

One-Way Data Flow

The DOM is still a parent and child structure, with grandchildren below. What components add is a rule about who has control: properties go down, events go up.

The parent TodoApp owns the tasks array, which is the state. It gives each TodoItem what it needs as props (text and done), so data flows down. The item only displays what it receives. When the user toggles it, the item cannot edit the array itself, so it calls the onToggle() function the parent handed it, and the event bubbles up. The parent then decides what actually changes and re-renders, sending fresh props back down.

The child never edits the parent's state directly. It calls a function the parent handed it, and the parent decides what changes.

  • A child never edits its own props; it only displays them, just as a function should not reach out of its module and mutate its caller's variables.
  • Every child has its own scope: they are the same widget with different data. That is why signalling upwards through an event is the convenient route: each child reports what happened to it, and the parent, which can see everything, decides.
  • Data moves in only two well-defined directions, and nothing beyond them. That is what keeps a large component tree (parents, children, grandchildren) predictable.

Trace of ticking one task off:

  1. The user clicks the checkbox in one TodoItem.
  2. The item calls onToggle(), the function it was given.
  3. TodoApp updates its tasks array (the state).
  4. React re-renders, and the changed task arrives at its item with new props, done now true.

Practice Questions

These are scenarios, not definitions. Think them through before looking anything up.

1. The stolen session. A university portal sets its login cookie as Set-Cookie: session_id=... with no further attributes, and the site is also reachable over plain HTTP. A student pastes a clever comment into a discussion forum on the portal, and later a classmate's account is used without their password. Walk through, step by step, how the attacker could have got hold of the session. Which two cookie attributes close which holes, and why would setting only one of them still leave you exposed? What would still be possible even after both are set?

2. The leaked table. A small shop's user table leaks. Alice and Bob chose the same password. In version A the shop stored plain text, in version B an unsalted hash, in version C a salted hash. For each version, what can an attacker conclude about Alice and Bob and about other users on other sites? Then explain why this same shop, after the leak, can still offer a "forgot password" button, what exactly that email contains, and what it tells you about what the shop actually knows.

3. One query, two programs. You write list_instructors.php and list_instructors.js running the same query. A friend opens each one in a browser. Describe what they see in each case, and what extra pieces the Node.js version needs before it can serve the same listing to a browser. Which parts of the lecture's "web server plus application plus database" picture does each piece map to? Finally, a user types Comp. Sci.' OR '1'='1 into a search box that feeds the query: how do the two programs differ in what happens, and why?

4. Where does the count live? A feed shows fifty posts, each with a LikeButton. The product manager now asks for two changes: (a) swap the heart for a thumbs-up, and (b) show "Total likes on this page" in a header bar. Where would you make change (a), and how many places does it touch compared with the three-file approach? For change (b), where must the like counts live, and what must flow down and what must bubble up for the header and the buttons to stay in agreement? What goes wrong if each button keeps its own private count?

5. Refresh and sign-out. You tap Like on a post and the number jumps from 56 to 57 without the page flashing. Trace what the browser and the server each do, and say which layer stays unchanged throughout. Then refresh the page: depending on how the app was built, the count may be 56 or 57. Explain what decides which one you see, and which kind of state was lost or kept. Last, if you sign out and the cart you had filled is still there when you sign in again tomorrow, explain which pieces (cookie, session record, account row) were deleted at sign-out and which one is holding your cart.
