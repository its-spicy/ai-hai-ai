The Road Ahead

This module is about data and the server side. Everything a web page shows you — an inbox, a shopping cart, a bank balance — is data, and the server side is mainly concerned with handling it: how it is managed, where it is stored and how it is changed.

The module covers these topics:

  • Databases, from first principles: why files alone were not enough, and what a DBMS adds.
  • The relational model and SQL: tables, keys, and the query language behind almost every app.
  • CRUD: the four operations that cover practically everything an application does to data.
  • Backend systems and web servers: what runs behind the scenes once a request leaves the browser, including a first look at PHP and Node.js.
  • Sessions, cookies and authentication: how a stateless protocol remembers who you are. This was touched on in the context of HTTP and is revisited here from the server-side programming point of view.

By the end, you should be able to explain why database systems are required instead of plain file storage, use SQL and the CRUD operations (the fundamentals of any relational database), start with server-side programming, and understand sessions and authentication.

The question that motivates everything. Every time you refresh your inbox or reload your shopping cart, some state has changed. Put three items in a cart, add a fourth, wander off for an hour and come back, and the cart still remembers exactly where you left off. So:

  • Where is that data remembered?
  • Where is that memory stored?
  • How are insertions, deletions and value changes performed on it?

That is the key question of this module.

Life Before Databases

Any computer already has a file system as part of its operating system: organized drives, a directory structure, naming schemes, and file handling with authentication and access control. So why was it not enough for large-scale data management?

Early applications were not very data-driven. They stored data directly in files, either as plain text or as one file per record type. As applications grew, this arrangement caused five recurring problems, each of which maps to a capability a database system later had to provide.

Problem What goes wrong
Redundancy and inconsistency Duplicated facts drift out of sync
Difficulty accessing data Every new question needs a new program
Integrity buried in code Rules are scattered, not stated once
Fragile under concurrency Simultaneous updates are silently lost
No central solution A DBMS solves all of these in one place

Redundancy and inconsistency

The same fact duplicated across files can silently drift out of sync. If a piece of data exists in several copies and an update reaches only one of them, the copies disagree, and nobody notices.

Difficulty accessing data

Every new question means writing a brand-new program. Imagine a file of bank account holders and the query "all account holders whose names start with the letter A". If records were simply appended at the end as they arrived, the list is not sorted alphabetically, so the program must perform a linear search and read the entire file before it can answer. You cannot jump straight to the record you care about, and the overhead of going through files is large.

Integrity buried in code

Rules such as "an account balance cannot go negative", or "a telephone number field always takes 10 digits (plus maybe a country code)" are integrity rules. A database can enforce them at the moment data is entered, and data that breaks the rules is simply not stored. With files, such rules live scattered inside every program that touches the data instead of being stated once, so any data can slip in.

Fragile under concurrency

Reading is harmless as long as nobody changes the data. The trouble begins when several people use the same file-based entry together. Suppose three people access one record and one of them performs an update: one of the others may still see the outdated copy while another sees the new one. There is no guaranteed synchronization. When several write operations hit the same data at the same time, the state value gets messed up. This is a race condition, to be studied later.

Note for Review: The slide's phrase "silently lose an update" is the important part. Two people read a balance of 500, one adds 100 and one subtracts 200, and both write back. Whoever writes last wins, so one of the two changes simply vanishes without any error message. Keep this picture in mind; it returns when concurrency control is discussed.

Where this matters in the real world

A database system exists to solve exactly these problems in one place. Today nearly every serious web application stands on one: banking and finance, universities and colleges, hospitals, airlines and travel, retail and e-commerce. They need real-time updates, huge numbers of entries kept consistent, and many concurrent users. Think of an airline reservation system, where bookings arrive from all over the country or the globe at the same moment, yet the accesses must not conflict with each other.

What Is a DBMS

A Database Management System (DBMS) is software that sits between an application and the raw data on disk. The data physically lives on storage (secondary and tertiary storage, with RAID-style arrangements that keep multiple copies for fault tolerance and backup). The DBMS is what accesses this raw data and lets applications use it seamlessly, while meeting all the requirements that files failed to meet.

The DBMS plays three roles. It defines structure through a schema, which is the blueprint or template of the data. It guards integrity through constraints that the system itself enforces. And it manages concurrent access so many users can read and write safely at the same time.

The three jobs in detail

  • Defines structure. A schema describes what the data looks like before any of it exists. For a university database storing students, every student entry has a roll number, name, address, enrolled subjects, grades and department, and every entry sticks to that structure.
  • Guards integrity. Constraints are enforced by the system itself, not by every program that touches the data. For example, if a date of birth is declared to follow the DDMMYYYY format, the database checks it on every insert. The format can be anything, but whatever is specified at the start is enforced forever, because the template is a rigid structure.
  • Manages concurrent access. Many users can read and write at the same time without conflict or inconsistency in the state of the data.

Well-known examples: MySQL, PostgreSQL, Oracle, SQL Server and SQLite (also Neo4j, which is not relational).

Data Models at a Glance

A data model is a set of tools for describing data, its relationships, and the constraints on it. What a schema looks like depends on the model chosen.

The relational model organizes data into tables, has been the dominant model since the 1980s, and is the focus of this module. The Entity-Relationship (ER) model is used mainly for designing a database before it is built. Object-based and semi-structured models cover object-relational databases and formats like XML/JSON for looser structure. The older network and hierarchical models mostly gave way to the relational model by the 1980s.

Design phase and development phase

Building a database happens in two phases.

  1. Design phase. From the requirement analysis of the business (a university, an online shop, an airline reservation system, anything), decide the entities and the relationships between them. Draw an ER diagram (or a UML / class diagram) to visualize and structure them.
  2. Development phase. Build it: each entity gets one table, and each relationship is realized as a table too.

An entity can be anything the system focuses on. In a university database, a student, a teacher and a course are all entities. A student and a teacher are human beings while a course is not, and that does not matter. A relationship such as takes connects entities and also gets its own table once the design is realized.

These requirements (entities, relationships, keys) must be analyzed carefully at the very beginning, because the schema built in the development phase is fixed. Changing a skeleton after the data is flowing is painful.

The Relational Model

In the relational model, every piece of data lives in a table, formally called a relation. When an entity is converted to tabular form, you get multiple rows and columns.

  • Rows are tuples. Each row represents one record. In a teacher table, every instructor gets one row (one tuple).
  • Columns are attributes. Each column holds one kind of fact. For a teacher these could be an ID, a name, the department they belong to, the courses they teach.
  • Order does not matter. A relation is technically an unordered set of tuples, even though tools usually display them in some order. A newly joined instructor is just added to the end, and ordering is something done later, during display, searching or access.

Formally, a relation is a set of tuples drawn from the domains of its attributes:

r⊆DID​×Dname​×Ddept_name​×Dsalary​

Ted Codd proposed the relational model in 1970. This work later earned him the ACM Turing Award, the most prestigious award in computing.

Here is the anatomy of a relation. The ER design gives an entity (for instance Teacher), which is realized as a table. Rows running down the table are the tuples, and the header names across the top are the attributes.

ID name dept_name …
t1 … … …
t2 … … …
t3 … … …

Rows are the tuples, header cells are the attributes.

Each row is one tuple (call them t1​,t2​,…). The first, t1​, is the instructor with ID 10101, named Srinivasan, in Computer Science, earning 65000. Each record is one instructor, and the column headers describe what each value means.

Schema vs Instance

A database schema is its logical structure: what tables exist and what columns each one has. For this table the schema is instructor(ID, name, dept_name, salary), a four-field template, and it never changes just because rows are added. The instance is the actual data in the database at one moment in time, and it changes constantly.

Schema Instance
Nature Static Dynamic
What it is Logical structure Data at one moment
Changes when rows are added? Never Always
Programming analogy Type definition Value of a variable at runtime

Schema in detail

The schema gives each field its characteristics. In the lecture's illustrative sketch:

  • ID is a number, 8 digits long.
  • name is a string, up to 20 characters (shorter is fine, longer is not).
  • dept_name is a string with a fixed maximum length.
  • salary is a number of limited digits.

So the schema fixes which column is what, what the domain (the range of values) of each column is, and which constraints apply. All of this is decided at the design stage. Once decided, it is the bare-bones skeleton of the table: you do not change it at run time, and every record must follow it. You cannot leave a field empty where it is required, drop a field for some tuples, or add an extra attribute for only some tuples.

Instance in detail

Whatever the table contains right now is one instance of the database. Add a new entry (say a made-up ID with some name, department and salary) and you get a different instance of the same table. Delete a row and the instance changes again. The physical state of the table changes dynamically, but the schema stays put.

Physical data independence

Physical data independence means the physical storage can change (say, adding an index) without touching the logical schema that applications rely on. The relational database supports this.

Note for Review: Do not confuse "the schema never changes at run time" with "the schema can never be changed". Schema changes exist (the ALTER command appears in the DDL section), but they are deliberate, rare design decisions, never a side effect of adding a row.

Keys

Keys are essential for accessing data and for connecting tables to each other. Think of a key as a unique anchor for each tuple.

  • Superkey: any set of columns whose values uniquely identify a row.
  • Candidate key: a superkey with no redundant columns. It is minimal.
  • Primary key: the candidate key a designer chooses as the official identifier, e.g. ID in instructor.
  • Foreign key: a column whose values must appear as a primary key in another table. This is what links tables together.

In mathematical form, a set of attributes K is a superkey of relation r when no two different tuples agree on K:

∀t1​,t2​∈r:t1​=t2​⇒t1​[K]=t2​[K]

and K is a candidate key when it is a superkey and no proper subset K′⊂K is itself a superkey.

Working through the instructor table

  • {ID,name} is a superkey. The pair (10101, Srinivasan) picks out exactly one tuple.
  • {dept_name} alone is not a key, since several tuples share a department. The same goes for {salary} alone.
  • {ID} is a candidate key, because it is minimal. Chosen as the identifier, it becomes the primary key.
  • {name} is a poor choice as a key. There could be another Srinivasan in a different department, so names can repeat.

Pro-Tip: Exams love the chain superkey ⊇ candidate key ⊇ primary key. Every candidate key is a superkey, but a superkey such as {ID,name} is not a candidate key if a smaller part ({ID}) already identifies rows. The primary key is simply the one candidate key you pick.

Foreign keys

Take two tables, instructor and department. Department holds the department information: name, building, budget. To relate them, one column in instructor is mapped to a column in department. The column in department is the primary key, and the matching column in instructor is the foreign key. This linking is compulsory in a relational database. Here, dept_name in instructor is a foreign key referencing the department table.

Keys in action: Students, Courses, Enrollments

In a Students table, both roll_no and email could each identify a student uniquely, so they are both candidate keys, but only one column (here, student_id) is chosen as the primary key. A pair like (roll_no, email) also identifies rows uniquely, but it is not minimal, since roll_no alone does it, so it is only a superkey and not a candidate key.

In Courses, course_code is unique (a candidate key) alongside the chosen primary key course_id. title is not a key, because the same title may be offered for different programs, such as undergraduate and graduate levels.

Enrollments is a third table that connects the two. It has its own primary key enrollment_id, plus student_id and course_id as foreign keys (each the primary key of its own table), and a grade, which obviously cannot be a key because hundreds of rows share the same grade. One student can enroll in many courses and one course has many students, so Enrollments resolves the many-to-many relationship, with one row per (student, course) pair.

This is why such relationships have to be identified early: the entities, the relationships and the keys are all decided at the design stage, before the fixed schema is built.

The University Database

From here on, SQL examples draw on one running example: a small university database with five tables.

Table Attributes
department dept_name, building, budget
instructor ID, name, dept_name, salary
student ID, name, dept_name, tot_cred
course course_id, title, dept_name, credits
takes / teaches which student took which course and the grade earned; which instructor taught which course

Remember the contrast: the schema is static (the logical structure), while the instance is dynamic (the state of the data, continuously changing over time).

Table relationships at a glance

In an ER diagram each entity is a box, and the lines between boxes show how they are connected (sometimes attributes are drawn as ovals outside the box). Reading the diagram:

  • Department connects to course (which department offers which courses) and to instructor.
  • An instructor is tied to a department, not directly to a course or a student.
  • A student is tied to courses through takes, and to a department through the course path.
  • The labels 1 and N give the nature of each relationship: many instructors belong to one department (N to 1), one department offers many courses, one student can take many courses, and many takes entries can point to one course (many students take the same course).

Foreign keys turn separate tables into one connected database. A 1 means exactly one matching row, and an N means many matching rows on the foreign-key side. In the diagram dept_name is the primary key of department and a foreign key in instructor and course; course_id is the primary key of course and a foreign key in takes; and ID is the primary key of student and a foreign key in takes.

The primary key of takes

Look at takes(ID, course_id, grade). The pair (ID, course_id) together forms its primary key. Neither can do it alone: one student can take many courses, so the same ID appears many times, and one course is taken by many students, so the same course_id appears many times. Only the combination identifies one tuple uniquely.

Note for Review: takes is a bridge table with a composite primary key, built from two foreign keys. In the Students/Courses/Enrollments example the same job was done with a separate surrogate key enrollment_id. Both designs are valid ways to resolve a many-to-many relationship.

Data, Metadata and SQL

Every database has two layers: the data itself, and the structure that organizes it.

  • Data: the actual values stored in rows, such as a specific student's name or a specific course's credit count. Each tuple is data.
  • Metadata: data about the data: table names, column names, data types, and constraints like PRIMARY KEY. This is the schema itself.
  • SQL (Structured Query Language): how you work with a relational database, by shaping its metadata and manipulating its data. First you define the schema (build the template that will hold the data). After the data is populated and instances are created, you manage that data in many ways.

SQL splits into families of commands, one for each job. The two used constantly are DDL and DML.

DDL vs DML

In SQL code, the words written in capitals are keywords: they are parsed and actioned, meaning each one triggers something. Names like a table name are variables and can be anything you choose.

DDL: Data Definition Language

DDL shapes the structure, which is the metadata. It is the schema language. The three commands are CREATE, ALTER and DROP.

CREATE TABLE builds a table, with the attributes and constraints listed inside the brackets. ALTER TABLE changes an existing table; here it adds a column called email, of type VARCHAR(50) (a variable-length string up to 50 characters), to Students. DROP TABLE deletes the whole table. 

-- schema.sql
CREATE TABLE Students (...)

ALTER TABLE Students
  ADD email VARCHAR(50)

DROP TABLE OldStudents

DML: Data Manipulation Language

DML works with the values, which is the data. The commands are SELECT, INSERT, UPDATE and DELETE.

INSERT INTO adds data row by row. SELECT ... FROM ... WHERE reads data in a customized way: every tuple matching the condition (here, roll_no = 'CS101') is the outcome. UPDATE ... SET changes a field. DELETE FROM removes rows. Notice that for update and delete, the WHERE clause first selects the tuple you want to change, and only then is the change performed. 

-- queries.sql
INSERT INTO Students VALUES (...)

SELECT name FROM Students
  WHERE roll_no = 'CS101'

UPDATE Students SET email = ...

DELETE FROM Students WHERE id = 1

Run DDL once, when you design or change the schema. Run DML constantly, as the application reads and writes data.

Pro-Tip: If UPDATE or DELETE has no WHERE clause, it applies to every row of the table. UPDATE Students SET email = ... with no condition overwrites the email of every student. This is a classic real-world accident, so always decide which tuples before deciding what change.

A Brief History of SQL

  • SQL began as SEQUEL, developed at IBM's San Jose Research Lab as part of the System R project in the 1970s.
  • It was renamed Structured Query Language (SQL) after a trademark conflict, and was later standardized by ANSI and ISO.
  • SQL-92, SQL:1999, SQL:2003: successive standards added more features over the decades (and obsoleted some).
  • SQL is declarative, not procedural. A procedural language states how something is to be done. SQL focuses on the what: a query says what data you want, not the steps to fetch it. The keywords are commands whose implementation is already built in. You say "insert", "delete" or "add", and you never describe the logic of achieving it.
  • It remains, by a wide margin, the most widely used database language in commercial use today.

Note for Review: Declarative means you describe the result, like ordering a dish at a restaurant. Procedural means you hand over the recipe. SQL is the ordering part; the DBMS is the kitchen.

Defining a Table

Here is a detailed CREATE TABLE example. It specifies not just which attributes exist but also what kind of values each can take, plus constraints.

ID is a fixed-length character field of 5. name is a variable-length string of up to 20 characters and carries not null, so no tuple may have a blank name. dept_name is a variable string and salary is numeric(8,2). The last three lines are constraints: the primary key is ID, and dept_name is a foreign key that references department, which is how the instructor table is connected to department. 

-- schema.sql
create table instructor (
  ID        char(5),
  name      varchar(20) not null,
  dept_name varchar(20),
  salary    numeric(8,2),
  primary key (ID),
  foreign key (dept_name)
    references department
);

Data types

Type Meaning
char(n) / varchar(n) fixed / variable-length text
int, smallint whole numbers
numeric(p,d) fixed-point, e.g. numeric(8,2) for money
real, float(n) floating point

Reading numeric(8,2)

In numeric(p,d), p is the total number of digits and d is how many of them come after the decimal point. For numeric(8,2):

p−d=8−2=6 digits before the point,d=2 digits after it

so the largest salary it can hold is 999999.99.

not null and primary key are integrity constraints: the database itself now refuses to store a row that breaks them. This is the "integrity stated once" promise from the start of the lecture, now in actual code.

Note for Review: char(5) always occupies 5 characters, while varchar(20) takes only as much space as the value needs, up to 20. Pick char for values that always have the same length (like a 5-digit ID) and varchar for things like names.

The SELECT Statement

Basics

select picks columns, from picks tables, and where filters rows. Think of it in the order select, from, where, even though SQL executes from from first. Here, every row of instructor whose department is Computer Science is matched, and only the name column is kept. 

-- query.sql
select name
from instructor
where dept_name
  = 'Comp. Sci.';
name
Srinivasan
Katz
Brandt

In relational algebra terms the where part is the selection σ (it picks rows) and the select part is the projection π (it picks columns):

πname​(σdept_name=’Comp. Sci.’​(instructor))

So the process is: first scan and keep all tuples that satisfy the condition, then project the name attribute, so only the name column arrives and not the full set of attributes.

DISTINCT

distinct removes duplicate rows from the result, the way a set naturally would. Without it, the dept_name column would list one entry per instructor. With it, the 10 instructor rows collapse to 5 distinct departments. 

-- distinct.sql
select distinct
  dept_name
from instructor;
dept_name
Comp. Sci.
Finance
Music
Physics
History

Filtering with WHERE and sorting with ORDER BY

Comparison operators (=, <>, <, >, between) combine with and, or, not. In the filter query, two conditions are joined with and, so a row must satisfy both to be selected: the department is Comp. Sci. and the salary is above 80000. Of the three Comp. Sci. instructors, only Brandt clears $80,000, and since the select list names only name, that is all that is shown. 

-- filter.sql
select name
from instructor
where dept_name
    = 'Comp. Sci.'
  and salary > 80000;
name
Brandt

The sort query selects two columns (name, salary) and orders the result by salary in descending order. order by defaults to ascending unless you add desc. It applies to one attribute, the one by which the entire result is ordered. 

-- sort.sql
select name, salary
from instructor
order by salary desc;
name salary
Einstein 95000
Brandt 92000
Wu 90000
Gold 87000
Singh 80000
Katz 75000
Srinivasan 65000
Califieri 62000
El Said 60000
Mozart 40000

Note for Review: Notice Singh earns exactly 80000, and that he does not appear in a salary > 80000 filter. The > operator is strict. Boundary conditions like this are a favorite source of off-by-one mistakes in queries, so check them against the data.

Pro-Tip: The result of a query is itself a table. The rows come back in some order, but a relation is an unordered set (as seen in the relational model). If you want a guaranteed order, you must ask for it explicitly with order by.

Practice Questions

  1. The double booking. An airline stored seat availability in a flat file read by many booking agents across the country. Two agents simultaneously read "1 seat left on flight X", and both confirm a booking. Trace what happens step by step, and explain which of the five file-system problems this is. Then say which DBMS responsibility would have to be involved to prevent it, and why enforcing this rule in each agent's own program would still be fragile.

  2. Choosing the anchor. A table Employee(emp_id, email, phone, name, dept) has these properties: emp_id and email are unique per employee, phone is unique except that two family members at one company sometimes share a number, and name can repeat. List all the minimal sets that are guaranteed to be candidate keys, explain why {emp_id,email} is a superkey but not a candidate key, and argue which candidate key you would choose as the primary key and why. What would break if you chose phone?

  3. Designing a hospital. A hospital wants to track patients, doctors and appointments. A patient may see the same doctor several times, and a doctor sees many patients. Decide the tables, their primary keys and their foreign keys. Explain why appointments needs its own table, and discuss whether the primary key of that table should be a composite of two foreign keys or a separate identifier, given that repeat visits exist.

  4. Predict the result. On the sample instructor relation, predict the exact output of select distinct dept_name from instructor where salary > 80000;. How many rows come back with and without distinct? Now suppose someone runs update instructor set salary = 70000; by mistake, with no where. Describe the instance afterwards, and say whether the schema changed and why.

  5. Schema or instance? The university wants to record a phone number for every instructor. Classify each of these actions as a change to the schema or to the instance, and name whether it is DDL or DML: (a) adding the phone column, (b) filling in a phone number for Wu, (c) adding a new instructor, (d) creating an index to speed up lookups by name. Then explain how (a) can be allowed when the lecture says every tuple must follow the structure, and what physical data independence guarantees about (d) for the applications that already use instructor.
