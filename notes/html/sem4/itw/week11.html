1. Recap and Roadmap

In the previous class we built the foundation of the database and back-end module: what a database system is, the relational model, and how an ER (Entity-Relationship) diagram describes entities and their relationships, which then become tables (relations) made of tuples. We separated data from metadata, and we separated two families of SQL commands:

  • DDL (Data Definition Language): creates or deletes the container, that is, the table and its schema (attributes, data types, constraints).
  • DML (Data Manipulation Language): works on the contents, that is, inserting new data, modifying fields, and retrieving data.

SQL is a declarative language: we state what we want, not how the database should compute it. We also met the keys (primary, foreign, candidate) and a first select ... from ... where query.

Today we move from "what is SQL" to "what can SQL do". We use the university database as our running example: it contains tables such as instructor, teaches, department, student and courses. A key idea to carry forward is that the schema (the shape of the tables) stays fixed, while the state of the database (the rows inside) changes continuously with every insertion, update and deletion.

2. The SELECT Statement: Basics

The select ... from ... where structure is the backbone of data retrieval. Each keyword has a distinct job:

  • select is a placeholder for a comma-separated list of attributes (columns) you want in the result. Whatever follows select is simply the set of attributes projected into the output.
  • from names the table(s) the data comes from. With one table, it is just the table name; with several, they are listed (or joined) here.
  • where states the constraint the rows must satisfy. Text values go inside quotes and are matched exactly as written.

The query below asks for the names of all instructors in the Computer Science department. Only the name attribute is projected, but you are free to ask for more: select name, dept_name, salary would return all three attributes, each as its own column in the result.

Here dept_name = 'Comp. Sci.' is compared against the stored string, and only the tuples whose department matches exactly are selected. Only the name column of those tuples is then shown, so three instructors come back. 

select name
from instructor
where dept_name
  = 'Comp. Sci.';
name
Srinivasan
Katz
Brandt

Asking for more attributes, as noted above, simply widens the result:

select name, dept_name, salary
from instructor
where dept_name = 'Comp. Sci.';
name dept_name salary
Srinivasan Comp. Sci. 65000
Katz Comp. Sci. 75000
Brandt Comp. Sci. 92000

Reading Order versus Running Order

select picks columns, from picks tables, where filters rows. Think of the query in that order, because that is how it reads. But SQL actually executes from first, then where, and only then select: the database first needs to know which table to look in, then which rows qualify, and finally which columns to show.

A good mental model: the query is written in the order of what you care about (the answer), but processed in the order of what the machine needs (the data source first).

Removing Duplicates with DISTINCT

The instructor table can contain many instructors from the same department, so a plain select dept_name would repeat Computer Science or Music several times. distinct removes duplicate rows from the result, the way a mathematical set naturally would. You write it right after select, followed by the attribute whose distinct values you want.

The instructor table has 10 rows, but only 5 different departments. select distinct collapses the repeated values, so 10 instructor rows collapse to 5 distinct departments. 

select distinct
  dept_name
from instructor;

dept_name
Comp. Sci.
Finance
Music
Physics
History

3. Filtering with WHERE and Sorting with ORDER BY

Combining Conditions

The where clause accepts comparison operators (=, <>, <, >, between) and you can combine them with the logical connectives and, or and not. This lets you build conditions as precise as you need.

In this query, both conditions must hold at the same time: the instructor must be in Computer Science and earn more than 80000. Of the three Computer Science instructors (65000, 75000, 92000), only Brandt clears the bar. 

select name
from instructor
where dept_name
    = 'Comp. Sci.'
  and salary > 80000;
name
Brandt

Ordering the Result

order by presents the retrieved rows in an order you specify, based on one attribute. For numeric attributes such as salary the order is ascending or descending by value; for character/string attributes it follows alphabetical order. The default is ascending; add desc for descending. Note that order by only affects presentation: the data inside the table is not stored in sorted order.

Here the rows are sorted on salary from the highest to the lowest, because of the desc keyword. Without desc, Mozart (40000) would appear first instead of last. 

select name, salary
from instructor
order by salary desc;
name salary
Einstein 95000
Brandt 92000
Wu 90000
Gold 87000
Singh 80000
Katz 75000
Srinivasan 65000
Califieri 62000
El Said 60000
Mozart 40000

Note for Review — Pro-Tip: order by defaults to ascending. Forgetting desc when the question says "highest first" is one of the most common slips. Also remember that salary > 80000 is strict: Singh earns exactly 80000 and would not pass even if he were in Computer Science.

4. CRUD: The Four Operations Behind Every App

Every web application you will build or use is data-driven, and the data lives in a database. If you think about it carefully, almost everything an application does to stored data boils down to four operations, remembered by the acronym CRUD. (First the container must exist, which is DDL's job; CRUD is about populating and managing what goes inside it.)

Operation Meaning SQL command
Create add a new record insert
Read retrieve existing records select
Update modify an existing record update
Delete remove a record delete
  • Create adds a new entry to the database.
  • Read retrieves what is already there, usually by matching a pattern with a where constraint.
  • Update is a write operation: it modifies the value of some attribute of some tuple.
  • Delete removes records that satisfy a constraint.

Every button in a typical web app maps to one of these four: Save, Edit, Remove, or even just loading a page. When a page loads, the back end fetches data and shows it to the user (a Read); when the user changes something, the new state is written and reflected on screen, and a reload reads it again. All of it is the back end performing CRUD operations.

Note for Review — Pro-Tip: The acronym is CRUD (not "crude"). Exam questions often ask you to map a user action to its SQL command. Remember: Save → insert, Page load → select, Edit → update, Remove → delete.

5. Create: INSERT INTO

The insert into statement adds a new row to a table. All four fields (ID, name, dept_name, salary) need a value, and each value must follow the schema: salary cannot be text, and an ID defined as a 5-digit number cannot be alphanumeric. The schema's constraints are enforced at insertion time.

There are two forms:

  1. Positional form: only values are given, and they must come in exactly the column order of the table.

  2. Explicit form: you list the attribute names in brackets, and each value maps one-to-one onto the attribute at the same position.

    Naming the columns explicitly (second form) is safer: it still works even if the table's column order changes later. Both statements append their rows at the end of the table, because rows are not stored in any sorted order, so any new entry simply goes after the existing records. 

insert into instructor
values ('10211', 'Smith',
        'Biology', 66000);

insert into instructor
  (ID, name, dept_name,
   salary)
values ('10212', 'Ng',
        'Comp. Sci.', 72000);

Rows added to instructor:

ID name dept_name salary
10211 Smith Biology 66000
10212 Ng Comp. Sci. 72000

6. Read: SELECT, Revisited

So far select has used a single table. But course_id is not an attribute of instructor; it lives in the teaches table. To project attributes from two tables, both tables must appear in from, and a condition in where must say how their rows relate. Every attribute named in select must belong to some table listed in from, otherwise the query fails with an error.

Listing two tables in from and matching their IDs in where is a join: it combines rows from both tables that relate to each other.

This query matches each instructor with the courses they teach. The condition instructor.ID = teaches.ID links the two tables, and dept_name = 'Comp. Sci.' restricts the result to Computer Science instructors. Srinivasan and Katz each appear twice because they teach two courses each, and one instructor row is matched with every related teaches row. 

select name, course_id
from instructor, teaches
where instructor.ID
      = teaches.ID
  and dept_name
      = 'Comp. Sci.';

teaches (sample rows):

ID course_id
10101 CS-101
10101 CS-315
45565 CS-101
45565 CS-319
76766 CS-319

query result:

name course_id
Srinivasan CS-101
Srinivasan CS-315
Katz CS-101
Katz CS-319
Brandt CS-319

Why This Join Works: Keys

This is exactly where the primary key and foreign key meet. ID is the primary key of instructor. In teaches, neither ID nor course_id alone can identify a row: an instructor can teach several courses (so ID repeats) and a course can be taught by several instructors (so course_id repeats). Therefore ID and course_id together form the primary key of teaches, while ID on its own is a foreign key pointing back to instructor. The where condition matches foreign key against primary key.

Because one instructor can teach multiple courses, a single instructor ID appears in several teaches rows. The join anchors each of those rows to the right instructor, so we can show the instructor's name (from instructor) next to the course (from teaches).

Note for Review — Pro-Tip: Writing from A, B (a comma between tables) with no matching condition produces the cross product: every row of A paired with every row of B. The where condition is what filters this down to the meaningful combinations. If you forget the condition, you get a flood of spurious tuples. Exams love this one.

7. Update: UPDATE

Suppose every instructor earning less than 70000 should get a 5 percent raise. Doing this by hand means visiting each entry, calculating the new salary, and overwriting it. That is a lot of effort for hundreds of rows and invites manual errors. SQL automates it: update names the table, set says what to change, and where chooses which tuples are affected.

The new salary is computed from the old one:

new salary=salary×1.05

For example, 65000×1.05=68250.

Only the tuples satisfying salary < 70000 are chosen and updated; anyone earning 70000 or more is untouched. Note that the table below is only a before and after view of the affected rows. The update statement itself does not print this result: you have to run a select afterwards to check for yourself. 

update instructor
set salary = salary * 1.05
where salary < 70000;

Affected rows, before → after:

ID name salary (before) salary (after)
10101 Srinivasan 65000.00 68250.00
15151 Mozart 40000.00 42000.00
32343 El Said 60000.00 63000.00
58583 Califieri 62000.00 65100.00

Note for Review — Pro-Tip: In practice, update always needs a where clause. Leave it off, and every row in the table changes. Treat an update without where the way you would treat rm -rf without checking the path.

8. Delete: DELETE

delete from <table> removes rows, and the where clause selects which ones. Here we want to get rid of the Finance department entirely, so every instructor tuple associated with Finance is deleted.

Two rows match the condition and are removed (Wu and Singh), so eight of the original ten rows remain. delete removes whole rows, never individual column values; to clear just one field, use update and set it to null. 

delete from instructor
where dept_name = 'Finance';

Rows removed:

ID name dept_name salary
12121 Wu Finance 90000
76543 Singh Finance 80000

Ripple Effects Across Tables

Updates and deletes can propagate beyond a single table. Suppose a department table exists alongside instructor: deleting a department could mean that all employees affiliated with it lose their entries too. And what if an employee belongs to multiple departments? Whether you delete the employees first or the department first depends on the specific use case. These cascading implications must be managed and controlled, and there are several ways of doing that. We will not go into the details here, but you must be aware that one delete can touch more than the table you named.

9. Practical Scenario: CRUD for a To-Do App Database

Let us tie everything together with the to-do list from Module 4's MVC example. The tasks table has three attributes: an id, the text label describing the task, and a done flag recording whether it is completed. addTask() and toggleTask() in that example were really just insert and update all along.

The four statements walk the table through its whole life. After the insert, one task exists and done is false. After the update, that same row has done = true, and we select the row by its id. After the delete, the table is empty again. If the table held ids 1 to 6, the where id = 1 would match and remove only the one tuple whose id is 1. 

-- Create: a new task
insert into tasks
  (id, text, done)
values (1, 'Buy milk', false);

-- Read: everything on the list
select * from tasks;

-- Update: mark it done
update tasks set done = true
where id = 1;

-- Delete: clear a finished task
delete from tasks
where id = 1;

tasks table, step by step:

step id text done
after insert 1 Buy milk false
after update 1 Buy milk true
after delete — (table is empty) —

select * means "all attributes of all tuples", so the Read step shows the whole list.

10. Summarizing Data: GROUP BY and Aggregates

Aggregate Functions and GROUP BY

Often you do not want rows, you want a summary: how many tuples satisfy a condition, the total salary drawn by a department, the minimum salary in Accounts. Aggregate functions (count, sum, avg, min, max) summarize many rows into one value.

The first query averages the salary of Computer Science instructors. The where clause first keeps only the Computer Science tuples, and then avg runs over their salaries:

avg(salary)=365000+75000+92000​=3232000​≈77333.33

group by runs that summary once per group instead of once overall. Rows with the same dept_name are brought together, the average is computed on each group, and you get one result row per department.

On the left, avg(salary) returns a single one-line result for Computer Science. On the right, the same average is computed for each department separately. Notice that the Computer Science row of the grouped result equals the single value from the first query. Conditions in where can also be chained with and / or, for example age between 30 and 50 and city = 'Jodhpur' (assuming such attributes exist), before the aggregate is applied. 

select avg(salary)
from instructor
where dept_name
  = 'Comp. Sci.';
avg(salary)
77333.33 
select dept_name,
  avg(salary) as avg_salary
from instructor
group by dept_name;
dept_name avg_salary
Comp. Sci. 77333.33
Finance 85000.00
Music 40000.00
Physics 91000.00
History 61000.00

The keyword as renames a result column: avg(salary) as avg_salary gives the computed column a readable header. Because the value is a temporary, intermediate result, this alias is just a placeholder name that exists only in the output.

Summarizing Data with HAVING

ow a richer query that joins two tables, groups the result and filters the groups. Here e and c are aliases (short names) for Enrollments and Courses.

Step by step: JOIN ... ON c.course_id = e.course_id pairs each enrollment with its course. GROUP BY c.title forms one bucket of rows per course title. COUNT(*) counts the tuples in each bucket (* means "all tuples"), and ROUND(AVG(e.marks), 1) averages the marks rounded to one decimal. Finally HAVING COUNT(*) > 20 keeps only courses with more than 20 enrolled students. A course such as Operating Systems with only 10 enrollments would be dropped. 

SELECT c.title,
  COUNT(*) AS students_enrolled,
  ROUND(AVG(e.marks), 1)
    AS avg_marks
FROM Enrollments e
JOIN Courses c
  ON c.course_id = e.course_id
GROUP BY c.title
HAVING COUNT(*) > 20;

Result:

title students_enrolled avg_marks
Intro to Databases 42 78.3
Web Technology 35 81.7
Data Structures 51 74.2

COUNT, SUM, AVG, MIN and MAX collapse many rows into one summary row per group. HAVING filters groups; WHERE filters rows.

This is the full order in which a query is processed. where acts early, on individual rows, before any grouping exists. having acts later, on the finished groups, which is why it can use aggregates like COUNT(*), and where cannot.

11. Filtering with IN, BETWEEN, and LIKE

These keywords are very useful for pattern matching and for string handling. in and between are shorthand for chains of or / comparisons, so they do not add new power, they add convenience.

BETWEEN

salary between 60000 and 90000 is exactly the same as salary >= 60000 and salary <= 90000. Both give the same outcome; SQL gives you the flexibility to express the same task in different ways. Note that between is inclusive at both ends: Wu (90000) and El Said (60000) are in the result.

Seven instructors fall in the range. Mozart (40000), Einstein (95000) and Brandt (92000) are outside it and are filtered out. 

select name, salary
from instructor
where salary
  between 60000 and 90000;

name salary
Srinivasan 65000
Wu 90000
El Said 60000
Gold 87000
Katz 75000
Califieri 62000
Singh 80000

Note for Review — Behind the Scenes: different ways of writing the same query can have different processing costs. The cost depends on how many rows are accessed, in what order, whether rows or columns are filtered first, and whether the shorter table is matched against the longer one or the other way round. Crafting a query that uses the least processing and memory is a skill in itself, and an advanced topic for later.

IN

in is a subset-membership test: the attribute must belong to a given set of values. dept_name in ('Music', 'History') matches any department that is either Music or History, and it is the same as dept_name = 'Music' or dept_name = 'History'.

Three tuples belong to the set {Music, History}: Mozart from Music, and El Said and Califieri from History. 

select name, dept_name
from instructor
where dept_name
  in ('Music', 'History');
name dept_name
Mozart Music
El Said History
Califieri History

LIKE

like matches text against a pattern, using two wildcards: % matches any run of characters (including none), and _ matches exactly one character. So 'E%' means "starts with E".

The pattern 'E%' keeps every name whose first letter is E and ignores whatever follows. Einstein matches, and so does El Said, since his name also starts with E. (The lecture slide's output lists only Einstein, which is an oversight: by the pattern's own rule El Said belongs in the result too.) 

select name
from instructor
where name like 'E%';
name
Einstein
El Said

Patterns need care. Suppose you want all customers whose date of birth (or any date) belongs to the year 2026 and you do not know the exact stored format. Searching for just '%26' matches anything ending in 26, which includes 1926, 2026 and 2126 if they exist in your data. The fix is to make the pattern more specific, for example like '%2026'.

Note for Review — Pro-Tip: % = any run of characters, _ = exactly one. 'E%' = starts with E, '%E' = ends with E, '%E%' = contains E, '_E%' = second letter is E. Be specific with your pattern, or you will match more than you intend.

12. Subqueries: A Query Inside a Query

A subquery is a query nested inside another query, a clever way to compose a request. The inner query runs first and produces a value or a list; the outer query then filters against that result. Execution goes from the inside out.

Example 1: Above the Average

"Give me the name and salary of every instructor who earns more than the average salary." First, the inner query computes the average over all ten instructors:

avg(salary)=10746000​=74600

That number is then substituted into the outer where, which becomes salary > 74600.

The inner query returns a single value (74600), so the outer query can compare against it with >. Six instructors earn more than the average: Wu, Einstein, Gold, Katz, Singh and Brandt. 

select name, salary
from instructor
where salary >
  (select avg(salary)
   from instructor);
name salary
Wu 90000
Einstein 95000
Gold 87000
Katz 75000
Singh 80000
Brandt 92000

Example 2: Instructors Who Appear in teaches

"Tell me the names of instructors who teach at least one course." Their ID must appear somewhere in teaches. The inner query returns a list of IDs from teaches, and the outer query keeps those instructors whose ID is in that list. This gives the same information as a join, but written with a subquery instead.

Srinivasan, Katz and Brandt are the instructors whose IDs appear in teaches; instructors who teach nothing never make it into the list, so they are not selected. 

select name
from instructor
where ID in
  (select ID
   from teaches);
name
Srinivasan
Katz
Brandt

Subqueries: Another Example

"Give me the name and roll number of students who are enrolled and scored more than the average marks." This one has two levels of nesting:

  1. The innermost query, select avg(marks) from Enrollments, runs first and returns one number.
  2. The middle query selects the student_id values from Enrollments whose marks exceed that number.
  3. The outer query keeps the students whose student_id is IN that list, and projects their name and roll_no.

At every level the result of the inner query is replaced into the query around it, until the outermost query runs and produces the final answer. In the flow on the right you can see the three queries evaluated from the innermost outward. 

SELECT name, roll_no
FROM Students
WHERE student_id IN (
  SELECT student_id FROM Enrollments
  WHERE marks > (SELECT AVG(marks) FROM Enrollments)
);

Result:

name roll_no
Asha Verma CS101
Priya Shah CS118
Rohan Iyer CS104

Note for Review — Pro-Tip: Use > (or =, <) when the subquery returns a single value, and use IN when it returns a list. Mixing them up is a classic error.

13. JOIN Types at a Glance

Whenever you list several tables in from, you are performing a join: relating tables to each other. Set theory gives us the picture, with each table as a circle and the overlap as the rows that match on the primary key / foreign key relationship. Here, A = Students and B = Courses, matched through Enrollments. The attribute names on each side may differ (for instance SID in one table and student_id in another), but they represent the same thing.

After a join, the result has the columns of both tables. If A has 5 columns and B has 4, the joined table has 5+4=9 columns. Rows of the cross product are:

∣A×B∣=∣A∣⋅∣B∣

The join type decides which of those combinations are kept, and what happens to rows with no partner (the missing side is filled with NULL).

INNER JOIN

A JOIN B keeps only the rows that match in both A and B, that is, the overlapping region A∩B. Rows with no partner on the other side disappear from the result.

LEFT JOIN

A LEFT JOIN B (also called LEFT OUTER JOIN) keeps everything in A, plus the matches from B. Additional rows in A that have no partner are still included, and the B columns for those rows are filled with NULL. Unmatched rows that exist only in B are not taken.

RIGHT JOIN

A RIGHT JOIN B is the mirror image: everything in B, plus the matches from A, with NULL in the A columns where nothing matches.

FULL OUTER JOIN

A FULL JOIN B keeps everything from both, matched where possible. Wherever a row has no partner, the columns of the other side get NULL. It does not matter whether the orphan is on the left or on the right: every combination is accounted for.

Summary

Join type Rows kept NULLs appear for
INNER JOIN only rows that match in both A and B never
LEFT JOIN everything in A, plus matches from B B columns, if no match
RIGHT JOIN everything in B, plus matches from A A columns, if no match
FULL OUTER JOIN everything from both, matched where possible either side

Note for Review — Pro-Tip: FULL OUTER JOIN isn't supported in MySQL, so in MySQL you work with the inner join (or the left and right joins). A join is also an expensive operation: it consumes memory, searching and CPU cycles, which is why chains of many joins are a bottleneck for large, responsive systems (more on this in Section 16).

14. JOIN in Action: Who's Enrolled in What?

This query lists each student with the course they are enrolled in and the grade they got, for the course whose code is CS101. Three tables are involved, so two JOINs chain them together: Students to Enrollments, and Enrollments to Courses, via their keys.

  • S, E and C are aliases (short variable names for tables). They are optional but convenient.
  • Aliases also avoid ambiguity: if two tables have an attribute with the same name, S.name and C.name tell the database which table you mean.
  • The keyword ON introduces the matching condition for each join (primary key against foreign key).

Enrollments sits in the middle: it holds the foreign keys student_id and course_id that point to Students and Courses. The first join attaches each enrollment to its student, the second attaches it to its course, and where c.course_code = 'CS101' keeps only that course. 

SELECT s.name, c.title, e.grade
FROM Students s
JOIN Enrollments e
  ON e.student_id = s.student_id
JOIN Courses c
  ON c.course_id = e.course_id
WHERE c.course_code = 'CS101';

Result:

name title grade
Asha Verma Intro to Databases A
Rohan Iyer Intro to Databases B+
Meera Nair Intro to Databases A-

15. More SQL to Explore in Your Hands-On Session

SQL is a language you pick up with practice. It is impossible to cover all of it in the limited time of this course, but what matters is knowing what tools exist, because only then can you design a good query for a given problem. Use your hands-on session and your web development tasks to try these out.

Topic Commands What it is for
Date & Time CURDATE(), DATEDIFF(), EXTRACT() working with when something happened; check how these differ
String Functions CONCAT(), SUBSTRING(), LIKE '%pattern%' searching and reshaping text
Set Operations UNION, INTERSECT, EXCEPT combining the results of separate queries
Views CREATE VIEW save a query as a reusable virtual table
Transactions BEGIN / COMMIT / ROLLBACK the ACID guarantees behind safe updates
Constraints NOT NULL, UNIQUE, CHECK, DEFAULT rules the database enforces for you
Window Functions RANK(), ROW_NUMBER() OVER (...) ranking rows without collapsing them
Indexes CREATE INDEX speeds up lookups

Views

A view is a temporary, virtual presentation of the database. It makes no change to the real data and is not stored as a separate physical table. Views are used for access control: in a university database you do not want students to see faculty data, or some clients to see the administrator's view, so each party gets a view that exposes only its own slice. A view can also be a temporary placeholder where modifications are staged before they reach the actual storage. And you can save a complex query as a view, so you can re-run it on the current state of the data whenever needed.

Transactions

A transaction groups statements into one all-or-nothing unit: BEGIN the transaction, do the work, COMMIT if everything succeeds, and ROLLBACK if there is any fault. This provides atomicity. It is essential in finance and any real-time system where multiple parties try to update a shared resource, such as a bank account balance or the pool of available seats in a reservation system. For state consistency, simultaneous conflicting updates are not simply allowed. Transactions and the recovery system form a whole dedicated chapter of database systems.

Constraints

NOT NULL, UNIQUE, CHECK and DEFAULT are given during schema definition and become part of the attribute's domain. At insertion, update or deletion time, the database checks them, and if one is violated, an error-handling or recovery mechanism kicks in, or an error is thrown to tell the user that something is wrong and why.

Window Functions

Functions such as RANK() and ROW_NUMBER() OVER (...) let you rank or number rows without collapsing them into groups, which is the difference from GROUP BY: every row stays in the output.

Indexes

CREATE INDEX builds an indexing structure that speeds up lookups. Without an index the database performs a linear search, scanning the data from top to bottom, which costs O(n) work per lookup and becomes enormous for a huge database in time, CPU cycles and memory. Indexing is the same idea as in data structures, and it is used for performance benefits in operating systems and for page ranking as well. Indexing is again a dedicated chapter of its own.

16. Why Look Beyond Relational?

Relational databases are not the only kind of database. They are built on assumptions that stop fitting some modern problems:

  • Relational databases assume your data fits neatly into rows and columns, with the schema fixed up front. Every tuple must squeeze into that format.
  • Rigid schema — adding a genuinely new kind of data often means an ALTER TABLE migration across a live system. It also gives little room for the variety of data in use today, such as multimedia and objects.
  • Deeply connected data — "friends of friends of friends" means chaining JOIN after JOIN, which gets slow as the chain grows. A join is a costly affair (memory, searching, CPU cycles), and series of joins are the main bottleneck for a large-scale, responsive back end.
  • Scale and structure — logs, sensor streams (IoT) and huge datasets such as those of Facebook or Twitter don't always share one common shape (likes, reposts, comments and networks are all different kinds of data) or fit on one machine.
  • These pressures gave rise to "NoSQL", which is not a rejection of SQL, but a family of alternatives built for what relational wasn't designed for.

NoSQL is not one database but a family. Which member you pick depends on the use case, and each family is growing quickly with a lot of ongoing progress, so it is worth exploring as per your requirements. Graph databases are the one we look at next.

17. Graph Databases: Data as Relationships

A graph database stores data as a graph: a node is an entity, and an edge is the relationship between two nodes. Both nodes and edges can carry their own properties (attributes). In the small graph below, Asha is friends with Rohan, and Asha and Rohan are enrolled in DB, while Asha and Priya are enrolled in Web Tech. All the solid lines are ENROLLED_IN edges.

This is a pure graph abstraction, applied directly to data storage, updates and modification. The relationship is a first-class citizen, stored as an edge, so asking "who is connected to whom" does not need a chain of joins.

At production scale the same idea holds millions of nodes and billions of edges, drawn as huge clusters of densely connected communities. The good part is that graph databases scale well at this size.

Real-world uses:

  • Social graphs (LinkedIn, Facebook, Twitter)
  • Recommendation engines (Amazon, Netflix)
  • Fraud-detection networks
  • Google's Knowledge Graph

Tools such as Neo4j let you exploit the graph abstraction through graph APIs: you run searching and path-traversal algorithms to find the association between two nodes, or run complex queries that leverage these graph-related APIs.

Other non-relational families exist too: object databases, document databases and key-value stores. Use cases decide which one fits, and each is a growing field.

Note for Review — Pro-Tip: "NoSQL" does not mean "no SQL" or "SQL is bad". It means "not only relational". Banks still run on relational systems because transactions and consistency matter most there, while a social network's friend-of-friend search is where graphs shine.
